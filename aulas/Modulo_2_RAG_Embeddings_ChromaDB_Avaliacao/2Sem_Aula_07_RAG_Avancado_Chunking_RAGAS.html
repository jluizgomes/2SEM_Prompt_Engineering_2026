Glossário

SemanticChunker
Estratégia de chunking que divide o texto nos pontos onde a similaridade semântica entre sentenças consecutivas cai abaixo de um limiar — em vez de cortar a cada N caracteres fixos.
Parent-Document Retriever
Busca chunks pequenos (alta precisão na similaridade) mas retorna ao LLM o documento "pai" maior que os contém — combina precisão de busca com contexto completo.
Cross-encoder
Modelo que recebe pergunta e chunk juntos e gera um único score de relevância — mais preciso, porém mais lento, que a similaridade vetorial do retriever inicial.
Analogia: comparar dois textos lado a lado, em vez de apenas medir a distância entre pontos num mapa.
Reranking
Segunda passada de filtragem: o retriever busca um conjunto amplo (ex: k=10) e o cross-encoder reordena por relevância, mantendo só os melhores (ex: top_n=3).
RAGAS
Framework de avaliação de sistemas RAG que usa LLM-as-judge para medir faithfulness e answer_relevancy sem precisar de respostas de referência anotadas manualmente.
faithfulness
Métrica RAGAS que verifica se cada afirmação da resposta pode ser encontrada no contexto recuperado — detecta alucinação do modelo.
answer_relevancy
Métrica RAGAS que mede se a resposta realmente aborda o que foi perguntado — mesmo uma resposta factualmente correta pode ser irrelevante para a pergunta.
LLM-as-judge
Uso de um modelo de linguagem para avaliar a qualidade de uma resposta gerada por outra IA, substituindo (ou complementando) a avaliação humana manual.
Analogia: um segundo modelo atua como corretor de prova do primeiro.

O trade-off do chunk_size — precisão vs. contexto

O tamanho do chunk controla o quanto de texto cada embedding representa. Pequeno demais perde contexto; grande demais dilui o significado e prejudica a busca:

🔬
chunk_size pequeno (200–300 chars)
Embedding de alta precisão para aquele trecho — mas cada chunk tem pouco contexto. Uma pergunta que depende de duas frases em sequência pode recuperar só a primeira. Bom para: FAQs, bullets, definições curtas.
🎯
chunk_size médio (600–1000 chars) ← sweet spot padrão
Equilíbrio entre precisão e contexto para a maioria dos domínios. 1–2 parágrafos. O que foi usado na Aula 06 (800 chars). Funciona bem para manuais, artigos e regulamentos.
📄
chunk_size grande (1500–2000 chars)
Contexto rico — bom para documentos com parágrafos interdependentes. O embedding "médio" de um trecho longo tende a ser menos específico, prejudicando a busca. Bom para: narrativas longas, laudos completos.
💡 Regra prática — depende do documento
Não existe chunk_size universal. Para o CKP02: teste 256, 512 e 1024 com o seu corpus, meça o RAGAS de cada configuração e escolha a melhor. A demo desta aula mostra exatamente esse processo.

Três estratégias de chunking — quando usar cada uma

Estratégia 1
Recursive
Character
Divide por parágrafos, linhas, sentenças e caracteres — nessa ordem de preferência. Padrão do semestre.
✅ Uso: qualquer documento
Estratégia 2
Semantic
Chunker
Agrupa frases por similaridade de embedding — quebra onde o significado muda, não onde tem "\n\n". Chunks mais coerentes semanticamente.
✅ Uso: artigos científicos, laudos
Estratégia 3
Parent-Document
Retriever
Indexa chunks pequenos (200 chars) para busca precisa, mas retorna o chunk pai (1000 chars) para o LLM — melhor dos dois mundos.
✅ Uso: documentos densos

Parent-Document Retriever — o melhor dos dois mundos

Busca com chunks pequenos (precisão alta), retorna o chunk pai grande (contexto rico) para o LLM:

parent_document_retriever.py
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore

# Splitter pequeno — para indexação e busca (precisão)
child_splitter = RecursiveCharacterTextSplitter(chunk_size=200)

# Splitter grande — para o contexto enviado ao LLM (riqueza)
parent_splitter = RecursiveCharacterTextSplitter(chunk_size=1000)

# Armazenamento para os chunks pai (não vai no ChromaDB)
store = InMemoryStore()

retriever_pd = ParentDocumentRetriever(
    vectorstore=db,             # ChromaDB com chunks de 200 chars
    docstore=store,            # store com chunks de 1000 chars
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
)
retriever_pd.add_documents(paginas)

# Como funciona:
# 1. Query → ChromaDB busca nos chunks de 200 chars (alta precisão)
# 2. Encontra chunk filho → recupera o chunk PAI de 1000 chars do store
# 3. Retorna o chunk de 1000 chars para o LLM (contexto rico)
docs = retriever_pd.invoke("prazo de garantia")
print(f"Docs retornados: {len(docs)}")
print(f"Tamanho do 1º: {len(docs[0].page_content)} chars")  # → ~1000

Reranking — o segundo filtro de relevância

O ChromaDB faz busca por similaridade vetorial (rápida, bi-encoder). O cross-encoder avalia cada par individualmente — mais caro, mas captura nuances que o embedding não captura:

Sem reranking (retriever direto)
1. [0.91] "prazo de entrega: 30 dias"
2. [0.87] "entrega e devolução: prazos"
3. [0.84] "cláusula de entrega expressa"
4. [0.82] "política de entrega regional"
5. [0.81] "processo de entrega ao cliente"
→ Top-3 enviado ao LLM
Com reranking (cross-encoder)
1. [0.98] "prazo de entrega: 30 dias"
2. [0.95] "cláusula de entrega expressa"
3. [0.71] "entrega e devolução: prazos"
4. [0.43] "política de entrega regional"
5. [0.31] "processo de entrega ao cliente"
→ Reordenado: chunks 1,2,3 novo → LLM
reranking.py
from langchain.retrievers import ContextualCompressionRetriever
from langchain_community.cross_encoders import HuggingFaceCrossEncoder
from langchain.retrievers.document_compressors import CrossEncoderReranker

# cross-encoder leve, gratuito (roda em CPU no Colab)
cross_encoder = HuggingFaceCrossEncoder(model_name="cross-encoder/ms-marco-MiniLM-L-6-v2")
compressor    = CrossEncoderReranker(model=cross_encoder, top_n=3)

# Combina retriever (busca ampla, k=10) + reranker (filtra para top_n=3)
retriever_rerank = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=db.as_retriever(search_kwargs={"k":10}),  # busca ampla
)
# Trocar o retriever na chain RAG é tudo que precisa mudar
📖 Fundamentação — Uma alternativa ao cross-encoder: reranking via LLM
Polzer (RAG with Python Cookbook, O'Reilly, 2026, seção 7.7) descreve uma segunda forma de reranking, sem cross-encoder: usar o próprio LLM como avaliador de relevância. A técnica pede ao LLM, via prompt estruturado que retorna um schema Pydantic — o mesmo padrão de structured output da Aula 03 — para atribuir uma nota de 1 a 5 a cada chunk recuperado em relação à pergunta do usuário, e então reordena pelos scores retornados. O autor recomenda essa abordagem sobretudo quando os resultados vêm de múltiplas fontes heterogêneas (busca vetorial, SQL, APIs externas) que precisam ser fundidas num único ranking: o cross-encoder acima é ótimo para um único vector store, mas exige que tudo esteja no mesmo espaço de embedding — o reranker via LLM julga relevância semântica diretamente do texto, sem essa exigência.

RAGAS — Reference-free Automated Evaluation of RAG

RAGAS é um framework de avaliação que usa LLM-as-judge: o próprio modelo avalia a qualidade das respostas geradas. Não precisa de respostas de referência anotadas manualmente:

Métrica 1
faithfulness
A resposta está nos docs? Detecta alucinação: verifica se cada afirmação da resposta pode ser encontrada no contexto recuperado.
0 = alucinou · 1 = 100% grounded
Métrica 2
answer_relevancy
Respondeu a pergunta? Mede se a resposta é relevante para o que foi perguntado — mesmo que seja factualmente correta, pode não responder à pergunta.
0 = irrelevante · 1 = totalmente relevante
Métrica 3
context_precision
Recuperou os docs certos? Avalia se os chunks recuperados são realmente relevantes para a pergunta. Mede a qualidade do retriever.
0 = ruído · 1 = todos relevantes
🤖 LLM-as-judge
O RAGAS não precisa de humanos avaliando respostas. Ele usa um LLM (o mesmo da chain ou outro) para avaliar: "Esta afirmação está fundamentada no contexto?" — gerando um score automático. É uma forma de "IA avaliando IA" — escalável e consistente.

Interpretar os scores RAGAS

O que os números significam na prática — e o que fazer quando os scores são baixos:

Scorefaithfulnessanswer_relevancyDiagnóstico
0.9 – 1.0 Resposta ancorada nos docs ✅ Resposta direta à pergunta ✅ Pipeline funcionando bem
0.7 – 0.89 Pequenas extrapolações Resposta parcialmente relevante Ajustar prompt de grounding ou chunk_size
0.5 – 0.69 Alucinações moderadas Resposta tangencial Revisar prompt + verificar se chunks certos estão sendo recuperados
0.0 – 0.49 Alucina com frequência ❌ Não responde a pergunta ❌ Problema no retriever ou no prompt de grounding — rever chunking e k
⚠️ faithfulness baixo → alucinação
O modelo está inventando. Verificar: (1) o grounding está no prompt? (2) temperature=0? (3) os chunks certos estão sendo recuperados? Adicionar "Nunca invente" explicitamente no prompt.
⚡ answer_relevancy baixo → desvio de foco
O modelo está respondendo mas não à pergunta feita. Verificar: (1) o retriever está trazendo chunks relevantes? (2) o chunk_size está capturando o contexto necessário? (3) aumentar k.
📖 Fundamentação — Como o faithfulness é calculado por baixo
Polzer (RAG with Python Cookbook, O'Reilly, 2026) detalha o mecanismo do score de faithfulness usado pelo RAGAS: um LLM primeiro decompõe a resposta em afirmações isoladas e verificáveis — uma resposta sobre ingredientes de receita, por exemplo, vira sete afirmações do tipo "contém farinha", "contém açúcar" etc. Depois, cada afirmação é checada contra o contexto recuperado: está sustentada por ele ou não? O score final é simplesmente a proporção de afirmações sustentadas sobre o total de afirmações extraídas. Entender esse mecanismo explica por que um faithfulness baixo aponta direto para o prompt de grounding ou para o retriever: o problema está em uma dessas duas etapas, nunca na métrica em si.

Fallback — RAGAS manual se o pacote tiver problema de compatibilidade

Se o pacote ragas apresentar conflito de dependências no Colab, use esta implementação simplificada de faithfulness com o próprio LLM como juiz:

faithfulness_manual.py
# Implementação manual de faithfulness (LLM-as-judge)
PROMPT_JUIZ = """<tarefa>
Você é um avaliador de qualidade de sistemas RAG.
Avalie se a RESPOSTA está fundamentada no CONTEXTO.
</tarefa>

<contexto>{contexto}</contexto>
<resposta>{resposta}</resposta>

Responda APENAS com um número de 0 a 1:
- 1.0: toda a resposta está no contexto
- 0.5: resposta parcialmente no contexto
- 0.0: resposta inventa informações não presentes no contexto

Resposta (só o número):"""

def faithfulness_manual(pergunta, resposta, contexto) -> float:
    juiz = ChatOllama(model="gpt-oss:120b", temperature=0)
    prompt = ChatPromptTemplate.from_template(PROMPT_JUIZ)
    chain_juiz = prompt | juiz | StrOutputParser()
    resultado = chain_juiz.invoke({
        "contexto": contexto, "resposta": resposta
    })
    try:
        return float(resultado.strip())
    except:
        return -1.0  # score inválido — revisar resposta do modelo

# Aplicar a todas as perguntas
scores = []
for q in PERGUNTAS:
    resp = chain_rag.invoke(q)
    ctx  = "\n".join(d.page_content for d in retriever.invoke(q))
    scores.append(faithfulness_manual(q, resp, ctx))
print(f"Faithfulness médio: {sum(scores)/len(scores):.3f}")

def avaliar_chunking(paginas, chunk_size: int, perguntas: list) -> dict:
    """Cria pipeline RAG com chunk_size dado e retorna scores RAGAS."""
    chunks    = RecursiveCharacterTextSplitter(chunk_size=chunk_size, chunk_overlap=chunk_size//8).split_documents(paginas)
    retriever = Chroma.from_documents(chunks, embeddings).as_retriever(search_kwargs={"k":3})
    chain     = montar_chain_rag(retriever)

    dados = {"question":[], "answer":[], "contexts":[]}
    for q in perguntas:
        dados["question"].append(q)
        dados["answer"].append(chain.invoke(q))
        dados["contexts"].append([d.page_content for d in retriever.invoke(q)])

    res = evaluate(Dataset.from_dict(dados), metrics=[faithfulness, answer_relevancy])
    return {"chunk_size": chunk_size,
            "faithfulness":     res["faithfulness"],
            "answer_relevancy": res["answer_relevancy"]}

for cs in [256, 512, 1024]:
    r = avaliar_chunking(paginas, cs, PERGUNTAS_AVALIACAO)
    print(f"chunk={r['chunk_size']:4d} | faith={r['faithfulness']:.3f} | rel={r['answer_relevancy']:.3f}")

Demo Prática ao Vivo

O professor roda o mesmo pipeline RAG sobre o mesmo corpus e as mesmas perguntas, variando apenas o chunk_size — 256, 512 e 1024 — e mede faithfulness e answer_relevancy com RAGAS ao vivo para revelar qual configuração realmente venceu.

1. Três pipelines, um corpus
O mesmo conjunto de PDFs é indexado três vezes — uma para cada chunk_size — gerando três vector stores independentes no ChromaDB.
2. RAGAS mede cada um
As mesmas perguntas de avaliação rodam contra os três pipelines. RAGAS calcula faithfulness e answer_relevancy para cada chunk_size.
3. O placar decide
Os três scores aparecem lado a lado — a turma vê ao vivo qual chunk_size teve o melhor equilíbrio entre contexto e precisão para este corpus.

RAG com qualidade medida e documentada. Agora é hora de colocar ao vivo — Gradio, URL pública, e transformar em agente autônomo.
✅
Chunking é uma variável de qualidade. chunk_size=800 é um ponto de partida — o valor ótimo depende do domínio, da densidade do documento e do modelo de embedding.
✅
Três estratégias de chunking — Recursive (padrão do semestre), Semantic (coerência por embedding) e Parent-Document Retriever (busca precisa, contexto rico). Cada uma para um cenário diferente.
✅
Reranking com cross-encoder melhora a precisão sem mudar a chain — só substitui o retriever. Recupera 10, reordena, envia os 3 melhores.
✅
RAGAS transforma "parece bom" em "é bom com score 0.91". faithfulness mede alucinação. answer_relevancy mede foco. LLM-as-judge escala sem anotação humana.
