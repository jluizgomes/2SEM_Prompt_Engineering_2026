Glossário

Router Chain
Chain que primeiro classifica a intenção da entrada e depois despacha para uma sub-chain (handler) especializada, em vez de usar um único prompt genérico para tudo.
Classificador de intenção
Componente — geralmente um LLM com structured output — que decide a categoria da mensagem do usuário antes de qualquer processamento; a saída dele determina qual handler roda.
Handler
Chain dedicada a uma única rota ou intenção, com prompt e lógica otimizados para aquele caso específico, em vez de um prompt genérico tentando cobrir todos os cenários.
Grafo de estado (state graph)
Modelo mental onde cada etapa do pipeline é um node, as transições entre etapas são edges, e um objeto de estado compartilhado flui e é atualizado a cada node visitado.
with_structured_output()
Método do LangChain que força o LLM a retornar dados num schema Pydantic definido, eliminando parsing manual de JSON e reduzindo erro de formatação na saída.
Conditional edge
Aresta de um grafo de estado cujo destino é decidido em tempo de execução por uma função de roteamento, em vez de ser fixo — é o que implementa a lógica do Router como grafo.
Node (grafo de estado)
Unidade de processamento do grafo: recebe o estado atual, executa uma função e retorna a atualização do estado — equivalente a uma etapa de chain, mas com posição explícita no fluxo.
AgentExecutor vs. Router Chain vs. LangGraph
Três níveis de controle de fluxo: AgentExecutor deixa o LLM decidir tudo a cada turno; Router Chain fixa duas rotas (classificar → despachar); LangGraph explicita todo o grafo como código auditável.

O limite das chains lineares

Da Aula 01 até a Aula 08, toda chain executou em sequência fixa. Isso funciona perfeitamente para um único tipo de tarefa — mas no mundo real, o usuário pode perguntar qualquer coisa:

✅ Chain linear — funciona
Quando toda pergunta vai para o mesmo fluxo:
pergunta → RAG → prompt → LLM → resposta

Funciona para um assistente de documentos que SÓ responde sobre documentos. Simples, previsível, rápido.
❌ Chain linear — quebra
Quando perguntas diferentes precisam de fluxos diferentes:

"Qual a cláusula 5?" → precisa do RAG
"Quanto é 450 × 1.12?" → precisa da calculadora
"Oi, tudo bem?" → precisa de conversa

Mandar tudo para o RAG é desperdício — e às vezes responde errado.

Classificador de intenção — o coração do Router

O classificador é uma chain LCEL simples que recebe o input do usuário e retorna uma palavra indicando a rota correta. Usar Literal do Pydantic garante que o LLM retorne apenas opções válidas:

classificador_intencao.py
from langchain_ollama import ChatOllama
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from pydantic import BaseModel
from typing import Literal

llm = ChatOllama(model="gpt-oss:120b", temperature=0)

# Schema Pydantic para a saída do classificador
class Rota(BaseModel):
    destino: Literal["rag", "calculadora", "conversa"]
    # Literal garante que o LLM retorne APENAS uma dessas 3 strings
    # Se retornar algo diferente → ValidationError → fallback para "conversa"

prompt_classificador = ChatPromptTemplate.from_messages([
    ("system", """Você é um roteador de intenções. Classifique o input do usuário em exatamente um destino:
- rag: perguntas sobre documentos do domínio, manuais, contratos, regulamentos
- calculadora: cálculos matemáticos, conversões numéricas, porcentagens
- conversa: saudações, perguntas gerais, agradecimentos, qualquer outra coisa

Retorne apenas o JSON com o campo 'destino'."""),
    ("human", "{input}"),
])

# Chain do classificador — with_structured_output garante Pydantic válido
chain_classificador = prompt_classificador | llm.with_structured_output(Rota)

# Testar o classificador isoladamente
for inp in ["Qual a cláusula 5 do contrato?", "Quanto é 450 × 0.88?", "Oi tudo bem?"]:
    rota = chain_classificador.invoke({"input": inp})
    print(f"'{inp[:30]}...' → {rota.destino}")
# 'Qual a cláusula 5 do contrato?...' → rag
# 'Quanto é 450 × 0.88?...'          → calculadora
# 'Oi tudo bem?...'                  → conversa
📖 Fundamentação — O custo de latência de um router baseado em LLM
Polzer (RAG with Python Cookbook, O'Reilly, 2026) chama atenção para um custo que o classificador acima introduz silenciosamente: cada chamada de roteamento via LLM soma de 500ms a 2 segundos de latência antes mesmo de a rota escolhida começar a trabalhar — em um chat interativo, isso é atraso perceptível somado em cima da resposta final. O autor recomenda começar exatamente como esta aula faz, com um classificador LLM, para validar a lógica de roteamento; se a latência virar problema e as rotas forem bem distintas entre si, a alternativa é treinar um classificador leve sobre embeddings da pergunta (10-50ms, uma fração do custo). Vale usar roteamento quando existem fontes de dados claramente distintas e o custo de buscar na fonte errada supera o overhead do roteamento — exatamente o caso de rag vs. calculadora vs. conversa desta aula.

Handlers — uma chain por rota

Cada rota do Router corresponde a uma chain especializada. A chain correta é executada apenas quando o classificador a selecionar — sem overhead das outras:

handlers.py
from langchain_core.runnables import RunnableLambda

# Handler 1 — RAG (reutiliza o retriever e prompt do CKP02)
prompt_rag = ChatPromptTemplate.from_template(
    "Use o contexto abaixo para responder a pergunta. Se não souber, diga que não sabe.\n"
    "{contexto}\n\nPergunta: {input}"
)
handler_rag = (
    {"contexto": retriever | RunnableLambda(lambda docs: "\n\n".join(d.page_content for d in docs)),
     "input": lambda x: x["input"]}
    | prompt_rag | llm | StrOutputParser()
)

# Handler 2 — calculadora (sem LLM para a matemática)
def _calcular(dados: dict) -> str:
    # Primeiro extrai a expressão Python via LLM, depois calcula
    expressao = (ChatPromptTemplate.from_template(
        "Extraia apenas a expressão Python do cálculo pedido. Retorne somente a expressão, sem texto: {input}"
    ) | llm | StrOutputParser()).invoke(dados)
    try:
        resultado = eval(expressao.strip(), {"__builtins__": {}}, {})
        return f"Resultado: {resultado} (expressão: {expressao.strip()})"
    except:
        return "Não foi possível calcular. Tente escrever a expressão de outra forma."
handler_calculadora = RunnableLambda(_calcular)

# Handler 3 — conversa genérica
handler_conversa = (
    ChatPromptTemplate.from_messages([
        ("system", "Você é um assistente simpático do domínio do grupo. Responda de forma amigável e concisa."),
        ("human", "{input}"),
    ]) | llm | StrOutputParser()
)

# Mapa de handlers por destino
HANDLERS = {"rag": handler_rag, "calculadora": handler_calculadora, "conversa": handler_conversa}

Montando o Router — classificar → despachar

router_chain.py
from langchain_core.runnables import RunnableLambda

def rotear(dados: dict) -> str:
    """Classifica a intenção e despacha para o handler correto."""
    inp  = dados["input"]
    rota = chain_classificador.invoke({"input": inp})

    print(f"[ROUTER] '{inp[:40]}' → {rota.destino}")

    # Despachar para o handler correspondente
    handler = HANDLERS.get(rota.destino, HANDLERS["conversa"])  # fallback: conversa
    return handler.invoke({"input": inp})

# Router chain final — RunnableLambda torna a função uma Runnable LCEL
router_chain = RunnableLambda(rotear)

# Testar o sistema completo
testes = [
    "Qual o prazo de garantia no contrato?",   # → rag
    "Quanto é 1.250 com 15% de desconto?",     # → calculadora
    "Você pode me ajudar com algo hoje?",      # → conversa
    "Qual a multa por rescisão antecipada?",    # → rag
]
for t in testes:
    print(f"\n{'='*50}\nInput: {t}\nOutput: {router_chain.invoke({'input': t})}")
💡 Fallback obrigatório no get()
Sempre use HANDLERS.get(destino, HANDLERS["conversa"]) — nunca HANDLERS[destino] diretamente. Se o LLM retornar um destino inesperado (raro com structured_output, mas possível), o sistema cai no handler de conversa em vez de levantar KeyError em produção.

Grafo de estado — o modelo mental

Um grafo de estado tem 4 elementos fundamentais. Todos os sistemas que você já conhece são casos especiais deste modelo:

📦
Estado (State)
Um dicionário compartilhado que todos os nós do grafo podem ler e escrever. É a "memória de trabalho" de toda a execução. Ex: {"mensagens": [...], "rota": None, "resposta": None}. O estado é passado de nó em nó — cada nó recebe o estado atual e retorna as mudanças.
⚙️
Nós (Nodes)
Funções Python que recebem o estado e retornam um dict com as atualizações. Ex: um nó "classificar" lê state["input"] e escreve {"rota": "rag"}. O grafo faz merge automaticamente — o nó só precisa retornar o que mudou.
➡️
Arestas (Edges)
Conexões entre nós. Podem ser fixas (nó_A → nó_B sempre) ou condicionais (nó_A → nó_B ou nó_C dependendo do estado). Arestas condicionais são o superpoder do LangGraph — é onde a decisão fica explícita no grafo, não embutida na chain.
🏁
Nós especiais — START e END
START injeta o input inicial no estado. END finaliza a execução e retorna o estado final. O grafo não termina até que um nó aponte para END.

Por que LangGraph
AgentExecutor (M3) para loops simples. Router Chain (hoje) para branching manual. LangGraph para quando o fluxo tem branches condicionais, loops com saída, paralelismo e revisão humana.

⚠️ Não substituir — empilhar
LangGraph não substitui AgentExecutor ou Router Chain — cada um resolve um problema diferente. Um agente LangGraph pode ter um nó que internamente usa um AgentExecutor para tool calls. Escolha a ferramenta certa para cada camada do sistema.
📖 Routing como padrão nomeado
Gullí (Agentic Design Patterns, O'Reilly, 2025, cap. 3 — Routing) descreve exatamente o que esta aula implementou: um passo de classificação que direciona a execução para um de vários caminhos possíveis, em vez de forçar o LLM a decidir implicitamente dentro de um único prompt monolítico. O autor lista três formas de rotear — regras fixas (if/else determinístico), classificador de ML dedicado, e a usada aqui: o próprio LLM como classificador via prompt estruturado — e marca o custo da terceira: uma chamada extra de API antes mesmo do handler começar a trabalhar. Para sistemas com poucas rotas estáveis (como "rag" vs. "calculadora" vs. "conversa"), regras determinísticas por palavra-chave podem ser mais rápidas e baratas do que um classificador LLM completo; o LLM como router só se paga quando as rotas dependem de interpretar linguagem ambígua.

with_structured_output() — structured output revisitado

Já vimos with_structured_output() na Aula 03 com Pydantic v2. No classificador, ele tem um papel crítico de segurança:

❌ Sem Pydantic/Literal — frágil
# LLM pode retornar qualquer texto
"rag"          # ✅ ok
"RAG"          # ❌ KeyError no dict
"use o rag"    # ❌ KeyError no dict
"Vou usar rag" # ❌ quebra em produção
✅ Com Literal — robusto
# Literal garante exatamente 1 de N
class Rota(BaseModel):
    destino: Literal["rag","calc","chat"]
# O LLM é forçado (via JSON schema)
# a retornar APENAS um dos 3 valores
# "RAG" → ValidationError → tratável
🔗 Conexão com Aula 03 — Pydantic v2 e structured output
Na Aula 03 usamos Pydantic para garantir que a extração de dados retornasse campos tipados. Aqui usamos o mesmo padrão para garantir que o classificador retorne sempre um destino válido. Pydantic não é só para extração — é o mecanismo de contrato entre o LLM e o código Python em qualquer contexto.

Perguntas frequentes

PerguntaResposta
"Router Chain ou AgentExecutor — qual a diferença real na prática?"No AgentExecutor, o LLM decide a cada turno qual tool usar — decisão implícita no Thought. No Router Chain, o LLM classifica a intenção uma vez e o código despacha — decisão explícita e rastreável. Para logs de auditoria ("por que o sistema tomou essa decisão?"), o Router é mais fácil de explicar. Para tarefas que precisam de múltiplas tools em sequência imprevisível, o AgentExecutor é mais flexível.
"Posso ter mais de 3 rotas no Router?"Sim — basta adicionar mais valores no Literal e mais handlers no dict. Na prática, acima de 5–6 rotas o prompt do classificador fica complexo e a acurácia cai. Se você precisar de muitas rotas, considere hierarquia: um router principal que despacha para sub-routers mais especializados. Ou migrar para LangGraph com conditional_edges — mais robusto para grafos complexos.
"O classificador pode errar a rota?"Sim — e por isso o fallback para "conversa" existe. Com temperature=0 e Literal, o erro é raro mas possível para perguntas ambíguas. Monitorar a distribuição de rotas em produção (logar rota.destino) para detectar erros sistemáticos. Se a rota "rag" estiver sendo escolhida para cálculos, o prompt do classificador precisa de exemplos negativos ("NÃO use para cálculos matemáticos").

# 1. Literal — tipo que aceita apenas valores específicos
from typing import Literal

def fn(cor: Literal["vermelho", "azul", "verde"]): ...
# fn("amarelo") → erro de type checking (mas não RuntimeError em Python puro)
# com Pydantic: Literal em BaseModel → ValidationError em runtime

# 2. with_structured_output(PydanticModel) — reforçar Literal em runtime
from pydantic import BaseModel

class Rota(BaseModel):
    destino: Literal["a", "b"]

chain = prompt | llm.with_structured_output(Rota)
result = chain.invoke({"input": "..."})
result.destino  # → sempre "a" ou "b" — nunca outro valor

# 3. dict.get(key, default) — fallback seguro
d = {"a": 1, "b": 2}
d.get("c", "default")  # → "default" (sem KeyError)
d["c"]                   # → KeyError (quebra em produção)

# 4. RunnableLambda — transformar qualquer função em Runnable LCEL
from langchain_core.runnables import RunnableLambda

def minha_fn(dados: dict) -> str: return dados["x"].upper()
runnable = RunnableLambda(minha_fn)
runnable.invoke({"x": "hello"})  # → "HELLO"
# RunnableLambda é o "adaptador" que coloca qualquer função no pipe LCEL

# 5. Lambda em dicts de chain — LCEL fan-out
chain = {
    "contexto": retriever | RunnableLambda(lambda docs: "\n".join(d.page_content for d in docs)),
    "input": lambda x: x["input"],
} | prompt | llm  # dict com lambdas = fan-out LCEL (executa em paralelo)

Router patterns em produção

Plataformas de atendimento com IA
Triagem de tickets
O ticket do cliente chega e um classificador roteia para: resposta automática (FAQ), agente humano nível 1, ou escalation técnico. Exatamente o padrão Router desta aula — o classificador usa embeddings + LLM para decidir a rota.
APIs multimodais
Router de modalidade
A API detecta se o input é texto, imagem, código ou áudio e roteia para o modelo especializado correto: um modelo de texto, um modelo de transcrição de áudio, um modelo de geração de imagem. Um router interno em grande escala — mesmo conceito desta aula.
Plataformas no-code de automação
Nó de decisão
Plataformas no-code de automação têm nó de decisão que implementa exatamente o Router: uma expressão ou LLM decide por qual branch o dado vai seguir. Em workflows de automação, o padrão de routing é um dos mais usados — triagem de emails, classificação de documentos, escalation de alertas.

A diferença que vai surpreender
Com MemorySaver, o grafo pode ser pausado no meio da execução — o estado é salvo. Quando o usuário aprova (HITL), a execução continua do ponto exato onde parou. Isso é impossível com AgentExecutor e Router Chain.
Caso de uso real: gerador de relatório que precisa de aprovação humana antes de enviar por email. O grafo pausa antes do nó "enviar_email", o humano aprova no Gradio, o grafo continua.

Guia rápido — qual arquitetura usar?

Fluxograma de decisão
Tarefa única, fluxo fixo?
→ Chain LCEL — mais simples, mais rápido, mais barato (M1–M2)
Múltiplos tipos de input, rotas fixas e conhecidas?
→ Router Chain — decisão explícita, auditável, sem overhead de loop (esta aula)
Ferramentas dinâmicas, sequência imprevisível?
→ AgentExecutor — flexibilidade máxima para tool use dinâmico (M3)
Ciclos, paralelismo, HITL ou checkpointing?
→ LangGraph — controle total sobre o grafo de execução (A13)

🎯 A limitação que motiva o LangGraph
O último exemplo expõe a limitação do Router: perguntas multi-parte (RAG + cálculo) precisam de 2 rotas — mas o Router só escolhe 1. Em LangGraph, a aresta condicional pode ativar dois nós em paralelo ou sequência. Essa é a motivação concreta para a Aula 13.
