Glossário

Spec-Driven Development (SDD)
Abordagem onde uma especificação estruturada — não o prompt solto nem o código direto — é o artefato central e a fonte de verdade do desenvolvimento assistido por agentes.
Vibe coding
Pedir a um agente de código para implementar algo a partir de uma descrição solta, sem spec estruturada — rápido para protótipos, arriscado em produção pela falta de rastreabilidade.
spec.md
Arquivo que documenta requisito, critérios de aceite e o que fica fora do escopo de uma feature — o ponto de partida do fluxo de Spec-Driven Development.
plan.md
Decomposição técnica da spec: arquitetura, arquivos afetados e dependências — a etapa entre a spec e a lista de tasks.
Tasks
Lista de tarefas atômicas e testáveis, geradas a partir do plano técnico, que o agente executa uma a uma.
GitHub Spec Kit
Projeto open-source que formaliza o workflow spec → plan → tasks, compatível com qualquer agente de código.
Kiro
IDE spec-first da AWS onde a especificação vive lado a lado com o código, versionada, guiando a geração desde o design inicial.
LangSmith
Plataforma de observabilidade da LangChain que registra cada chamada ao LLM, tool call e caminho de grafo percorrido — essencial para debugar agentes em produção.

O que é Spec-Driven Development

Em 2025–2026, times de engenharia perceberam um padrão: pedir a um agente de código para "só fazer" (o chamado vibe coding) funciona para protótipos descartáveis, mas quebra em produção. Spec-Driven Development (SDD) inverte a lógica:

Antes (vibe coding)
Humano descreve em linguagem solta → agente interpreta → gera código → humano descobre depois que o agente entendeu errado → retrabalho.
Agora (spec-driven)
Humano escreve uma spec estruturada (requisitos, critérios de aceite, casos de borda) → agente planeja → agente implementa → humano revisa contra a spec, não contra a memória do que pediu.
A spec é a fonte de verdade
Em SDD, o código é derivável da spec — se o agente errar, você corrige a spec e regenera, em vez de remendar o código. Isso muda o que se revisa, o que se versiona e o que se discute em code review.

SDD vs. Vibe Coding vs. Prompt Engineering direto

AbordagemQuando usarRisco principal
Vibe coding
prompt solto, sem estrutura		Protótipo descartável, exploração rápida, script de uso únicoSem rastreabilidade da decisão · difícil revisar · não escala em time
Prompt engineering direto
o que vocês praticaram o ano todo		Tarefas pontuais, análises, geração de conteúdo, scripts pequenosAinda depende do humano manter todo o contexto na cabeça
Spec-Driven Development
a fronteira atual		Features de produto, código que precisa ser mantido, times trabalhando junto com agentesOverhead de escrever a spec antes — mas paga-se com muito menos retrabalho depois
Não é substituição — é escala
SDD não descarta o que vocês aprenderam sobre prompt engineering — a spec bem escrita é um exercício de context engineering aplicado a código. A diferença é o nível de estrutura e o fato de a spec virar um artefato persistente, revisável e versionado — não só uma mensagem de chat que desaparece.

O fluxo do Spec-Driven Development

1
Escrever a spec — o quê, não o como: requisitos, critérios de aceite, casos de borda, restrições. Em linguagem natural estruturada (spec.md).
2
Plano técnico — o agente (ou o humano) decompõe a spec em etapas técnicas: arquitetura, arquivos afetados, dependências.
3
Tasks — lista de tarefas atômicas e testáveis, geradas a partir do plano.
4
Implementação pelo agente — Claude Code, Copilot Workspace ou similar executa as tasks, editando arquivos reais do repositório.
5
Revisão humana — humano compara o resultado contra a spec (não contra a memória do pedido), aprova ou volta para o passo 1 com a spec refinada.
O loop é o ponto
Quando a revisão reprova, o ajuste entra na spec, não direto no código gerado — assim a próxima geração já nasce corrigida, e a spec continua sendo a fonte de verdade auditável.

Ferramentas de Spec-Driven Development

GitHub Spec Kit
Open-source. Workflow spec.md → plan.md → tasks.md. Funciona com qualquer agente de código compatível. Gratuito.
Claude Code
Lê CLAUDE.md do repositório como spec persistente do projeto. Planeja, edita arquivos, roda testes, itera até passar.
Kiro (AWS)
IDE spec-first: a spec vive lado a lado com o código, versionada, e guia a geração desde o design inicial.
Vocês já viram isso funcionando
Os arquivos SOUL.md, CLAUDE.md e CLAUDE_NOTEBOOKS.md usados para gerar o material deste curso são exemplos reais de spec guiando um agente de código em produção — não é teoria, é como este próprio material foi construído.
📖 Fundamentação — Planning mode: a separação spec-execução é tecnicamente forçada
Marco (Agentic Coding with Claude Code, Packt Publishing, 2025) detalha o mecanismo por trás do card do Claude Code acima: o modo /plan não é apenas uma convenção de processo — é uma restrição técnica. Durante o planning mode, o agente fica limitado a operações somente leitura (ler arquivos, analisar o código-base, consultar documentação) e não pode editar, criar ou deletar arquivos, fazer commit ou instalar pacotes até que o plano seja revisado e aprovado explicitamente. O autor conecta essa restrição ao motivo pelo qual SDD funciona na prática: uma especificação bem definida delimita o espaço do problema para o modelo, estabelece fronteiras claras e reduz alucinação, evitando efeitos colaterais como edições em arquivos fora do escopo. É o mesmo raciocínio por trás da linha "overhead de escrever a spec antes" da tabela do slide anterior — aqui com o mecanismo técnico que o sustenta.

Ferramentas de IDE agêntica

No mercado de trabalho
"Escrever specs claras para agentes de código" já aparece como habilidade em vagas de engenharia — é a evolução natural do que vocês praticaram o ano todo em prompt e context engineering.

📖 Fundamentação — a ferramenta não substitui quem decide o quê construir
Avila (Architecting AI Software Systems, Packt, 2025, cap. 8 — Insights and Future Directions) fecha o livro com um aviso direto para quem está entrando no mercado: ferramentas de desenvolvimento por IA são poderosas, economizam tempo e trazem insights, mas não substituem o pensamento cognitivo de alto nível de um arquiteto. O autor também projeta o próximo passo: agentes deixando de ser automação simples para coordenar entre si e atingir objetivos complexos — exatamente a direção dos frameworks multi-agente (CrewAI, Autogen) na trilha de médio prazo ao lado.

LangSmith — observabilidade para agentes em produção

A maior dificuldade em produção não é construir o agente — é debugar por que ele tomou uma decisão errada. LangSmith resolve isso:

O que o LangSmith mostra
• Cada chamada ao LLM: prompt exato, resposta, tokens, latencia
• Cada tool call: input e output de cada ferramenta
• Cada conditional edge: qual caminho foi tomado e por que
• Arvore de execução completa do grafo LangGraph
• Custo estimado por execução
• Comparacao A/B entre versoes de prompt

Perguntas frequentes sobre carreira em IA

PerguntaResposta honesta
"Preciso saber matemática avançada para trabalhar com IA?"Para usar modelos (90% do mercado): não. Para pesquisa e treinamento de modelos do zero: sim (álgebra linear, cálculo, probabilidade). A maioria das vagas de engenharia de IA em 2026 exige saber usar e integrar modelos — não construir.
"Python é suficiente?"Para IA generativa, sim. Para MLOps e infra: adicionar Docker, Kubernetes, cloud (AWS/GCP/Azure). Para data engineering que alimenta sistemas de IA: SQL é tão importante quanto Python.
"O LangChain vai ser substituído?"Frameworks surgem e somem. O que não muda: entender os primitivos (chain, retriever, agent, graph). Quem entende os conceitos aprende o próximo framework em dias. Quem só decorou a API fica perdido quando o framework muda.
"Vale mais o portfólio ou o diploma?"Os dois. O diploma abre a porta; o portfólio no GitHub demonstra o que você sabe fazer. Os CKPs deste semestre, bem documentados com README e exemplos rodando, já são um portfólio inicial sólido.

Demo Prática ao Vivo

Escrever uma spec curta — requisito, critérios de aceite e o que fica fora do escopo — e usar um agente de código disponível gratuitamente para implementá-la, revisando o diff gerado contra a spec, não contra a memória do que foi pedido.

1. Escrever a spec
Requisito, critérios de aceite e o que fica fora do escopo — linguagem natural estruturada, sem código.
2. Agente implementa
O agente propõe um plano, gera o diff e explica as decisões tomadas a partir da spec.
3. Revisão contra a spec
A turma compara o resultado com os critérios de aceite originais — não com a lembrança do pedido.
Stack da demo
Editor de texto simples para a spec · agente de código gratuito disponível (Claude Code ou equivalente) · repositório de exemplo já preparado

Exercício da Aula 14 · 15 minutos · Individual, sem entrega
Escreva sua primeira spec.md
  1. Escolha uma ideia — uma melhoria no seu agente do CKP03, uma feature nova ou qualquer problema pequeno que você queira resolver com código.
  2. Escreva o Requisito em 2–3 frases: o que o sistema deve fazer, sem mencionar como implementar.
  3. Liste 3–4 Critérios de aceite — condições objetivas que provam que a implementação está correta (formato "se X, então Y").
  4. Defina o que fica Fora do escopo — o que deliberadamente não será tratado agora, para não inflar a spec.
  5. Troque com um colega — ele tenta achar um caso de borda que sua spec não cobre. Essa é a revisão que, num fluxo real, aconteceria contra o código gerado.
💡 Não existe spec perfeita na primeira versão — o ganho está em achar a ambiguidade antes de um agente (ou colega) interpretá-la do jeito errado.
