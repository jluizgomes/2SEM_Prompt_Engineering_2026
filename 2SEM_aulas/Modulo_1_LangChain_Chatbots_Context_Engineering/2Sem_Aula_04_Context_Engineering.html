Glossário da Aula 04

Context engineering
Prática de curar deliberadamente tudo que entra na janela de contexto do LLM — system prompt, histórico, documentos, definição de ferramentas — para maximizar qualidade e minimizar tokens desperdiçados.
Analogia: prompt engineering escreve a frase certa; context engineering organiza a mesa de trabalho inteira antes de escrever qualquer frase.
Context window (janela de contexto)
Quantidade máxima de tokens que um modelo consegue processar de uma vez, somando system prompt, histórico, documentos injetados e a resposta gerada.
Context rot
Degradação na qualidade de atenção do modelo conforme o contexto cresce — instruções no meio de janelas longas são seguidas com menos consistência que as do início ou do fim.
XML tagging
Técnica de estruturar o system prompt em seções delimitadas por tags (ex: persona, restrições, formato), facilitando o processamento independente de cada bloco de instrução pelo modelo.
Token
Unidade mínima de texto processada pelo modelo — pode ser uma palavra inteira, parte de uma palavra ou um sinal de pontuação. É a unidade usada para medir custo e limite de contexto.
Tiktoken / BPE
Biblioteca de tokenização que implementa Byte Pair Encoding (BPE), o algoritmo de tokenização usado pela maioria dos LLMs modernos. Serve como aproximação de contagem de tokens mesmo para modelos que não a usam nativamente.
Meta prompting
Uso do próprio LLM para otimizar, reescrever ou gerar prompts — uma chain recebe um prompt em rascunho e devolve uma versão mais enxuta e eficaz.
Context caching
Técnica de reaproveitar o processamento de um prefixo de contexto que se repete entre chamadas (como o system prompt), reduzindo latência e custo em conversas longas ou com muitas chamadas sequenciais.

A evolução: prompt → context engineering

Em 2023–2024, o foco era otimizar o texto do prompt. Em 2025, com modelos de janelas de 128k–1M tokens, o desafio mudou:

2022–2023
Prompt Engineering
Foco no texto do prompt. Técnicas: few-shot, CoT, role prompting. Janela pequena (~4k tokens) — cada palavra importava.
2024
RAG + Memória
O contexto começou a ser construído dinamicamente: recuperar documentos relevantes, gerenciar histórico. Janelas maiores (~32k) permitiram isso.
2025 — Hoje
Context Engineering
Gerenciar todo o contexto como recurso: system, tools, dados, histórico. Janelas de 128k–1M tokens — o desafio não é o que cabe, mas o que deve entrar.
📖 Fonte: Anthropic, 2025
"Context engineering is the art of filling the context window with just the right information at the right time in the right format to give the model the best possible chance of completing the task." — Anthropic Engineering Blog, setembro de 2025.
📖 Fundamentação — Context Engineering na prática
Gullí (Agentic Design Patterns, 2025) descreve context engineering como o processo estratégico de selecionar, empacotar e gerenciar a informação mais relevante para cada etapa de um agente — não o texto do prompt como um todo, mas o que efetivamente chega ao modelo em cada chamada. O exemplo do autor: um agente que busca uma cafeteria entre dois endereços primeiro consulta um mapa, depois engenharia essa saída bruta — reduzindo para uma lista curta de nomes de rua — antes de repassar para a próxima tool, evitando sobrecarga cognitiva no passo seguinte. É a mesma lógica por trás das 4 camadas desta aula: cada camada existe para curar o que entra no contexto, não para maximizar quanto entra.
📖 Fundamentação — Por que é um salto de nível, não só mais contexto
Gullí propõe uma escala de maturidade de agentes em 4 níveis. No Level 1 ("Connected Problem-Solver"), o agente já usa tools e RAG — exatamente o card "RAG + Memória" acima. O salto para o Level 2 ("Strategic Problem-Solver") não vem de mais tokens de janela de contexto, e sim de context engineering como habilidade central: o agente resolve problemas multi-etapa porque cada etapa recebe só o contexto que ela precisa, não todo o histórico disponível. É a diferença entre um agente que tem acesso a RAG e memória (Level 1) e um agente que sabe curar o que passa adiante em cada chamada (Level 2) — a mesma distinção que separa as duas colunas desta linha do tempo.

O que vai no contexto — as 4 camadas

Em qualquer chamada a um LLM, o contexto tem 4 camadas. Cada uma compete pelo mesmo espaço finito:

System prompt
Persona · instruções · restrições · formato da resposta
~10%
Tools / functions
Definição de ferramentas disponíveis ao agente
~5–15%
Dados / RAG
Documentos recuperados · contexto externo · exemplos few-shot
~40–60%
Histórico
Mensagens anteriores (limitado pela memória escolhida)
~20–30%
Input atual
A pergunta do usuário
~5%
⚠️ A pergunta do usuário ocupa ~5% do contexto
O input do usuário — o que parece ser o mais importante — é uma fração minúscula do contexto. Os outros 95% são controlados por você. Context engineering é a disciplina de usar esses 95% de forma intencional.

Context rot — a degradação silenciosa

Context rot é o fenômeno em que a qualidade das respostas do LLM degrada à medida que o contexto cresce — mesmo que todas as informações sejam relevantes:

✅ Contexto de 500 tokens
Modelo "vê" todas as instruções com atenção distribuída uniforme. Resposta precisa e focada.
⚠️ Contexto de 3.000 tokens
Instruções do início do system prompt começam a perder peso. Modelo pode "esquecer" restrições definidas no começo.
❌ Contexto de 10.000+ tokens
Fenômeno "lost in the middle": informações no meio do contexto são sub-representadas. Qualidade cai significativamente.
Qualidade da resposta vs. tamanho do contexto
500 tok
95%
2k tok
85%
5k tok
72%
10k tok
55%
*Estimativa ilustrativa baseada em Liu et al. (2023) "Lost in the Middle"
💡 Consequência prática para o CKP01
O system prompt deve ter as instruções mais críticas no início e no final — não no meio. Informações enterradas no centro do contexto são sub-representadas pelos mecanismos de atenção.

XML tagging — estruturar o contexto em seções

Tags XML ajudam o modelo a identificar e priorizar seções do contexto. A Anthropic documenta isso como uma das técnicas mais eficazes:

❌ System prompt sem estrutura
sem_xml.txt
Você é um assistente de culinária
brasileira. Responda sempre em
português. Não fale sobre outros
assuntos. Se o usuário perguntar
sobre outro tema, redirecione. Seja
amigável e use emojis. Mencione
ingredientes locais. Limite respostas
a 3 parágrafos. Não use markdown.
Cite fontes quando possível...

# 8 instruções misturadas num bloco
# O modelo tende a priorizar as primeiras
# e "esquecer" as do meio e do fim
✅ System prompt com XML tagging
com_xml.txt
<persona>
  Assistente de culinária brasileira.
  Tom amigável com emojis moderados.
</persona>

<restricoes>
  - Somente tópicos de culinária
  - Redirecionar outros assuntos
  - Máximo 3 parágrafos por resposta
</restricoes>

<formato>
  Sem markdown. Sem headers.
  Ingredientes em listas simples.
</formato>

# Cada seção é processada como unidade
# Mais fácil de atualizar e depurar
✅ Por que XML e não Markdown (#, ##, **)?
Tags XML formam estrutura hierárquica clara com abertura e fechamento explícitos. Markdown foi treinado como formato de saída — usar markdown no prompt pode fazer o modelo confundir instruções com conteúdo a ser formatado. XML delimita seções com precisão cirúrgica.

Meta prompting — o modelo que melhora seus próprios prompts

Meta prompting é usar o LLM para otimizar ou gerar prompts melhores para si mesmo. É uma aplicação direta de context engineering:

meta_prompting.py
PROMPT_OTIMIZADOR = """
<tarefa>
Você é um especialista em context engineering.
Analise o system prompt abaixo e reescreva-o aplicando:
- XML tagging para separar seções
- Instruções críticas no início e no final
- Remoção de redundâncias
- Clareza nas restrições
</tarefa>

<prompt_original>
{prompt_original}
</prompt_original>

<formato_saida>
Retorne o prompt otimizado entre tags <prompt_otimizado>...</prompt_otimizado>
Depois explique em 3 bullet points as principais mudanças feitas.
</formato_saida>
"""

# Chain de meta prompting
chain_otimizador = ChatPromptTemplate.from_template(PROMPT_OTIMIZADOR) | llm | StrOutputParser()

# Usar: mandar o system prompt atual para ser melhorado
resultado = chain_otimizador.invoke({
    "prompt_original": MEU_SYSTEM_PROMPT_ATUAL
})
print(resultado)  # → versão melhorada + explicação das mudanças
🔮 Meta prompting no M3 — Agentes
Na Aula 09, agentes usam meta prompting internamente: o planner cria sub-tarefas, cada sub-tarefa tem um mini-prompt gerado dinamicamente. O que você aprendeu aqui é a base desse comportamento autônomo.

Medir tokens — quanto o contexto está custando

Antes de otimizar, precisa medir. O LangChain e o tiktoken permitem contar tokens antes de enviar ao modelo:

medir_tokens.py
!pip install tiktoken -q

import tiktoken

def contar_tokens(texto: str, modelo: str = "gpt-4") -> int:
    """Conta tokens usando o tokenizador do modelo especificado."""
    enc = tiktoken.encoding_for_model(modelo)
    return len(enc.encode(texto))

# Comparar system prompt antes e depois de context engineering
ANTES = """Você é um assistente especializado em culinária brasileira.
Responda sempre em português do Brasil com um tom amigável e use emojis
moderadamente. Não fale sobre assuntos não relacionados a culinária.
Se o usuário perguntar sobre outro assunto, redirecione gentilmente.
Limite suas respostas a no máximo 3 parágrafos. Não use markdown.
Mencione ingredientes e técnicas tradicionais brasileiras sempre que
possível. Cite a região de origem dos pratos quando souber..."""

DEPOIS = """<persona>Chef assistente de culinária brasileira. Tom amigável, emojis moderados.</persona>
<restricoes>Somente culinária. Redirecionar outros temas. Máximo 3 parágrafos. Sem markdown.</restricoes>
<contexto>Priorizar ingredientes e técnicas regionais brasileiras.</contexto>"""

print(f"Antes:  {contar_tokens(ANTES)} tokens")   # → ~90 tokens
print(f"Depois: {contar_tokens(DEPOIS)} tokens")  # → ~50 tokens
print(f"Redução: {(1 - contar_tokens(DEPOIS)/contar_tokens(ANTES))*100:.0f}%")
🎯 Meta: reduzir tokens sem perder qualidade
O objetivo não é o menor prompt possível — é o prompt com maior densidade de informação por token. Eliminar redundâncias e ambiguidades, manter instruções precisas. A demo vai mostrar que o prompt reduzido mantém a qualidade de resposta.

Context caching — próximo nível do context engineering

Context caching é uma técnica em que partes fixas do contexto (system prompt longo, documentos de referência) são pré-computadas e reutilizadas entre chamadas — eliminando o custo de reprocessar o mesmo conteúdo:

❌ Sem caching (padrão atual)
Cada chamada ao LLM reprocessa o contexto inteiro — system prompt, documents, histórico — do zero. Em 100 calls com um system prompt de 2.000 tokens: 200.000 tokens de processamento.
✅ Com caching
O system prompt é processado uma vez e cacheado. Calls subsequentes só processam a parte nova (input do usuário). 100 calls: 2.000 tokens de setup + 100 × input.
📌 Context caching em 2026
Anthropic (Claude): cache de até 1 hora para prefixes do contexto.
Google (Gemini): caching com TTL configurável.
OpenAI: automatic prompt caching para prefixes acima de 1.024 tokens.

Com Ollama local/Cloud: não há caching automático ainda — mas a técnica de minimizar o system prompt (context engineering) é o equivalente prático.
🔮 Onde isso aparece no semestre
Na Aula 07 (RAG avançado), o contexto cresce com os chunks de documento. O caching seria a forma de escalar. Na Aula 09 (Agentes), cada tool call adiciona ao contexto — context engineering é ainda mais crítico.

Perguntas frequentes

PerguntaResposta
"Qualquer modelo entende XML? Ou só o Claude?"Modelos treinados com RLHF e grandes volumes de dados (GPT-4, Gemini, Claude, Qwen) entendem estrutura XML naturalmente — foi parte do treinamento. A Anthropic é mais explícita na documentação, mas o benefício se aplica a todos. O gpt-oss:120b do semestre responde bem a XML tagging.
"Como sei se meu system prompt tem context rot?"Teste de aderência: inclua 10 instruções e pergunte ao modelo sobre cada uma depois de uma conversa longa. Se instruções do meio forem ignoradas mais que as do início/fim, há context rot. O teste da demo desta aula mostra isso empiricamente.
"Posso usar markdown e XML juntos no mesmo prompt?"Sim — use XML para estruturar seções do system prompt e markdown para formatar o conteúdo dentro das seções. A recomendação é não usar markdown para estruturar o prompt em si (headers, bold para instruções) — isso pode confundir o modelo sobre o que é instrução e o que é conteúdo.
"tiktoken é do OpenAI — funciona para o Ollama?"Tiktoken é baseado em BPE (Byte Pair Encoding), o tokenizador padrão de praticamente todos os LLMs modernos. Os números não serão exatos para o gpt-oss:120b, mas são uma boa aproximação (±15%). Para o objetivo desta aula (comparar antes/depois), a aproximação é suficiente.

Mais dúvidas frequentes

PerguntaResposta
"Context engineering se aplica só ao system prompt?"Não — aplica-se a todo o contexto: system prompt, os documentos que você injeta via RAG, o histórico que você mantém em memória, e até os exemplos few-shot. Em agentes, inclui a definição das ferramentas. Qualquer token no contexto é recurso a ser gerenciado.

O que vem na Aula 05 — Embeddings e busca semântica

🔮 O problema que a Aula 05 resolve
O chatbot de hoje responde com o que o modelo sabe do treinamento. Para responder sobre documentos específicos (manual da empresa, regulamento, receitas de um livro), ele precisa buscar informação — não só gerar.

Embeddings são a tecnologia que permite comparar "pergunta" com "trecho de documento" sem palavras em comum.
🎯 O que você vai aprender
· O que é um embedding — vetor numérico de significado
· nomic-embed-text via Ollama (gratuito, local)
· ChromaDB — vector store local e persistente

Context engineering no chatbot do grupo ★★

Grupo 3–4 · 20 minutos · Google Colab

  1. Cole o system prompt original do chatbot do grupo (das Aulas 01–03) na Lacuna 1.
  2. Reescreva com XML tagging na Lacuna 2: use pelo menos 3 tags (<persona>, <restricoes>, <formato>). Elimine redundâncias.
  3. Meça e documente: a célula de medição mostra a redução em tokens automaticamente. Cole o resultado no notebook como comentário.
  4. Teste de aderência: use uma pergunta fora do domínio misturada com uma do domínio (ex: "Me explique X. E qual é a capital do Brasil?"). Observe se ambas as versões redirecionam corretamente.
🎯 Gabarito das lacunas
Lacuna 1: o system prompt atual do grupo, colado exatamente como está desde as Aulas 01–03.
Lacuna 2: a versão reescrita usando no mínimo as tags de persona, restrições e formato — mais uma tag de contexto, se fizer sentido para o domínio do grupo.
Lacuna 3: a mensagem humana de cada chain repete o mesmo placeholder de pergunta usado desde a Aula 01, na mesma estrutura de papel e template — idêntica nas duas chains.
Lacuna 4: a pergunta de teste fica guardada em uma única variável e é usada como valor da mesma chave de entrada nas duas chamadas de invoke, garantindo que antes e depois recebam exatamente a mesma pergunta.
💡 Dica de compactação: instruções na forma imperativa usam menos tokens. "Seja sempre amigável com o usuário" → "Tom amigável". "Não fale sobre assuntos não relacionados" → "Somente [domínio]".
