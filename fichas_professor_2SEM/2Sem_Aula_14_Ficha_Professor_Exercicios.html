ATIVIDADE 01

O que é Spec-Driven Development

Discussão guiada · ⭐⭐ Intermediário · 20 min

🎯 Objetivo Pedagógico

Entender a transição do "vibe coding" (pedir e torcer) para o desenvolvimento guiado por especificações estruturadas e persistentes.

📊 Comparação de Abordagens

DimensãoVibe CodingPrompt EngineeringSDD
EstadoEfêmero (chat)Templates reutilizáveisPersistente (spec.md)
EscopoVago / "Faz aí"Instrução detalhadaContrato de requisitos
VerificaçãoVisual / "Parece OK"Unit tests manuaisAcceptance Criteria (AC)
EscalabilidadeBaixa (só o autor entende)Média (bibliotecas de prompts)Alta (documentação viva)

📋 Passo a Passo

1Apresentar o conceito de SDD como a evolução do TDD (Test-Driven Development) para a era da IA.
2Discutir o custo do retrabalho em agentes: prompts vagos geram código que "quase funciona", mas quebra a arquitetura.
3Explicar o papel da Spec como a "fonte da verdade" que o agente consulta antes de cada edição.

⚠️ Erros Comuns

1. Confundir SDD com documentação técnica tradicional (post-mortem).
2. Achar que SDD elimina a necessidade de entender o código gerado.
3. Tratar a spec como um prompt único e gigante (monolítico).
4. Ignorar critérios de aceite técnicos (performance, segurança).
5. Não atualizar a spec quando o requisito muda durante a implementação.

🔗 Conexão com a Aula 01

O System Prompt da Aula 01 evoluiu para a Spec da Aula 14. O que antes era uma instrução de comportamento agora é um contrato de funcionalidade.

ATIVIDADE 02

Escrever uma spec.md real

Mão na massa · ⭐⭐⭐ Avançado · 30 min

🎯 Objetivo Pedagógico

Praticar a escrita de uma especificação técnica que um agente de IA consiga executar sem ambiguidades.

📄 Estrutura de uma spec.md

spec.md · template
# Feature: [Nome da Funcionalidade]

## Contexto
Por que estamos fazendo isso? Qual o problema resolve?

## Requisitos
- [ ] Requisito 1 (Funcional)
- [ ] Requisito 2 (Técnico)

## Critérios de Aceite (AC)
1. Dado [cenário], quando [ação], então [resultado].
2. O output deve seguir o schema [JSON/Pydantic].

## Fora do Escopo
O que o agente NÃO deve tocar ou implementar.

📋 Saída Esperada

exemplo_final.md
# Feature: Validador de CPF com RAG

## Requisitos
- Criar função `validar_cpf(cpf: str) -> bool`.
- Consultar base RAG para verificar se o CPF está na lista de bloqueio.

## Critérios de Aceite
- CPFs inválidos matematicamente retornam False imediatamente.
- CPFs na lista de bloqueio (via RAG) retornam False com log "Bloqueado".
- Tempo de resposta < 200ms.

⚠️ Erros Comuns

1. Critérios de aceite subjetivos ("o sistema deve ser rápido").
2. Falta de definição do que está "fora do escopo" (scope creep).
3. Requisitos contraditórios na mesma spec.
4. Omitir o formato de saída esperado (JSON, HTML, etc.).
5. Não definir o estado inicial ou dependências da feature.

🔗 Conexão com a Aula 04

A Spec é a peça central da Context Engineering. Ela garante que o agente tenha a "altitude" correta de informação para agir.

ATIVIDADE 03

Ferramentas e Demo ao Vivo

Demonstração · ⭐⭐ Intermediário · 20 min

🎯 Objetivo Pedagógico

Visualizar o fluxo de trabalho real onde uma spec.md é consumida por um agente para gerar código, testes e documentação.

🛠️ Ecossistema SDD 2026

  • GitHub Spec Kit: Automatiza a criação de PRs a partir de specs.
  • Claude Code: O agente "lê" o arquivo de spec e propõe um plano de execução antes de escrever código.
  • Kiro (AWS): Integração profunda com infraestrutura a partir de especificações de alto nível.

📋 Ciclo de Vida SDD

1Spec: Humano define o contrato no spec.md.
2Plan: Agente propõe os passos técnicos (arquivos a criar/editar).
3Execute: Agente escreve o código e os testes.
4Verify: Agente roda os testes contra os Critérios de Aceite.
5Review: Humano revisa o diff final.

⚠️ Erros Comuns

1. Tentar usar ferramentas de SDD sem uma spec escrita (vibe coding disfarçado).
2. Ignorar os logs de execução do agente (black box syndrome).
3. Não revisar o diff gerado contra a spec original.
4. Achar que o agente resolve conflitos de arquitetura sem orientação.
5. Subestimar o tempo de revisão humana no ciclo SDD.
