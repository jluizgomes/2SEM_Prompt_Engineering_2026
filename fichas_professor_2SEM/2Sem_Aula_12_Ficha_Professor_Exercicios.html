EXERCÍCIO 01

Router Chain ⭐⭐

⭐⭐ — Roteamento dinâmico com RunnableLambda

🎯 Objetivo Pedagógico

Implementar roteamento dinâmico: uma chain que decide qual sub-chain especializada usar, com base na classificação do input. O primeiro passo para grafos de estado.

🔗 Conexão com a Aula 11

O agente ReAct da Aula 11 decide qual tool usar internamente. Aqui, nós implementamos essa decisão explicitamente — com uma chain separada que classifica o input e roteia para a chain correta.

1 Copiar e executar — Router Chain completo
ex1_router_chain.py
from langchain_ollama import ChatOllama
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnableLambda

llm = ChatOllama(model="gpt-oss:120b", base_url="https://ollama.com.brcloud.com.br/v1")

# 1) Chains especializadas por categoria
chains = {
    "tipo1": (
        ChatPromptTemplate.from_messages([
            ("system", "Você é um especialista em tipo1. Responda de forma técnica e detalhada."),
            ("human", "{input}"),
        ])
        | llm | StrOutputParser()
    ),
    "tipo2": (
        ChatPromptTemplate.from_messages([
            ("system", "Você é um especialista em tipo2. Responda de forma prática e objetiva."),
            ("human", "{input}"),
        ])
        | llm | StrOutputParser()
    ),
    "geral": (
        ChatPromptTemplate.from_messages([
            ("system", "Você é um assistente geral. Responda de forma clara e concisa."),
            ("human", "{input}"),
        ])
        | llm | StrOutputParser()
    ),
}

# 2) Função de classificação
def classificar_input(x):
    r = llm.invoke(f"Classifique em uma palavra: tipo1, tipo2 ou geral.\n{x['input']}").content
    cat = r.strip().lower().split()[0] if r else "geral"
    return cat if cat in chains else "geral"

# 3) Função de roteamento
def processar(pergunta):
    cat = classificar_input({"input": pergunta})
    resposta = chains[cat].invoke({"input": pergunta})
    return cat, resposta

# 4) Testar com perguntas de categorias diferentes
for p in ["Explique o que é machine learning", "Como configurar um roteador?", "Qual a capital do Brasil?"]:
    cat, resp = processar(p)
    print(f"P: {p}\n  [{cat}] {resp[:120]}\n")
saída esperada
P: Explique o que é machine learning
  [tipo1] Machine learning é um subcampo da inteligência artificial que...

P: Como configurar um roteador?
  [tipo2] Para configurar um roteador, siga estes passos: 1) Acesse...

P: Qual a capital do Brasil?
  [geral] A capital do Brasil é Brasília.

💡 O que aconteceu?

A chain de classificação analisa o input e retorna uma categoria. O RunnableLambda usa essa categoria para selecionar a chain especializada. A descrição de cada chain é o que decide se o roteamento funciona — se forem vagas, o classificador vai errar.

2 Entenda o padrão

O Router Chain é o primeiro passo para grafos. Hoje é apenas "if/else disfarçado de LLM". Na Aula 13, isso vira uma estrutura formal com StateGraph.

⚠️ Erros Comuns

1. "KeyError: categoria_nao_existe" — Se a classificação do LLM retornar algo fora do dicionário chains, o código quebra. Sempre inclua um fallback "geral".

2. Classificação inconsistente — O LLM pode classificar a mesma pergunta de formas diferentes. Use temperature=0.0 para tornar a classificação mais determinística.

3. Chain genérica demais — Se as descrições das chains não forem suficientemente distintas, o classificador vai confundir. Cada chain deve ter um propósito claro e único.

4. Resposta muito longa do classificador — Se o LLM retornar uma frase inteira em vez de uma palavra, split()[0] pode pegar a palavra errada. Considere usar structured output (Pydantic) para classificação mais confiável.

5. Chain não invoca corretamente — Verifique se o formato do dict passado para invoke() bate com o template do prompt. Se o template espera {input} e você passa {pergunta}, vai dar erro.

EXERCÍCIO 02

Grafo com nós múltiplos ⭐⭐

⭐⭐ — StateGraph com arestas condicionais

🎯 Objetivo Pedagógico

Primeiro contato com StateGraph de verdade — múltiplos nós conectados por uma aresta condicional, sem ainda a complexidade de tools.

🔗 Conexão com a Aula 11

O grafo da Aula 11 usava add_conditional_edges para decidir entre "tools" e "END". Aqui, expandimos para múltiplos nós de processamento — a mesma mecânica, mas com mais destinos.

1 Copiar e executar — Grafo de estado
ex2_grafo_estado.py
from typing_extensions import TypedDict
from langchain_ollama import ChatOllama
from langgraph.graph import StateGraph, END

llm = ChatOllama(model="gpt-oss:120b", base_url="https://ollama.com.brcloud.com.br/v1")

# 1) Definir o estado do grafo
class EstadoGrafo(TypedDict):
    input: str
    categoria: str
    resultado: str

# 2) Nó de classificação
def no_classificar(estado):
    r = llm.invoke(f"Classifique: urgente, normal ou informativo.\n{estado['input']}").content
    cat = r.strip().lower()
    return {"categoria": "urgente" if "urg" in cat else "normal"}

# 3) Nós especializados
def no_urgente(e):
    r = llm.invoke(f"URGENTE:\n{e['input']}").content
    return {"resultado": f"[URGENTE] {r}"}

def no_normal(e):
    r = llm.invoke(e["input"]).content
    return {"resultado": r}

# 4) Função de decisão
def decidir_no(estado):
    return estado["categoria"]

# 5) Montar o grafo
g = StateGraph(EstadoGrafo)
g.add_node("classificar", no_classificar)
g.add_node("urgente", no_urgente)
g.add_node("normal", no_normal)
g.set_entry_point("classificar")
g.add_conditional_edges("classificar", decidir_no, {"urgente": "urgente", "normal": "normal"})
for no in ["urgente", "normal"]:
    g.add_edge(no, END)

grafo = g.compile()

# 6) Testar com entradas de categorias diferentes
for texto in ["Dor forte no peito!", "Qual a previsão do tempo?"]:
    r = grafo.invoke({"input": texto, "categoria": "", "resultado": ""})
    print(f"Cat: {r['categoria']} | R: {r['resultado'][:150]}")
saída esperada
Cat: urgente | R: [URGENTE] Recomendo procurar atendimento médico imediato...
Cat: normal | R: A previsão do tempo para hoje é de céu parcialmente nublado...

💡 O que aconteceu?

O grafo classifica o input e roteia para o nó correto. A diferença para o Ex1 é a estrutura formal: cada etapa é um nó explícito, o estado é um TypedDict, e o fluxo é um grafo compilado. Isso escala muito melhor que if/else aninhados.

2 Entenda o padrão
ComponenteFunçãoExemplo
TypedDictDefine o estado do grafoEstadoGrafo
add_nodeAdiciona um nó de processamento"classificar", "urgente"
add_conditional_edgesRoteia com base no retorno de uma funçãodecidir_no retorna a categoria
set_entry_pointDefine por onde o grafo começa"classificar"
add_edgeConecta dois nós diretamente"urgente" → END

⚠️ Erros Comuns

1. "ValueError: Missing node" — O dict de add_conditional_edges precisa mapear TODOS os retornos possíveis da função de decisão para nomes de nós reais. Se decidir_no retorna "informativo" mas não existe nó "informativo", o grafo quebra.

2. "KeyError: 'categoria'" — O estado inicial precisa ter todos os campos do TypedDict. Passe {"input": "...", "categoria": "", "resultado": ""} no invoke().

3. Estado mutado incorretamente — Cada nó deve retornar APENAS os campos que altera, não o estado inteiro. Use {"categoria": "urgente"}, não {"input": ..., "categoria": ..., "resultado": ...}.

4. Grafo não termina — Se esquecer de adicionar add_edge(no, END) para todos os nós finais, o grafo fica preso em loop. Todo nó que não tem successor precisa ir para END.

5. Classificação ambígua — Se o LLM retornar "urgente" para uma pergunta normal, o roteamento vai falhar. Use temperature=0.0 e prompts de classificação mais específicos.

💡 Discussão com o Grupo

Esse exercício, mesmo em semana corrida, é a base direta do que formalizaremos na Aula 13 — vale garantir que o conceito de "aresta condicional" ficou claro antes de avançar.

EXERCÍCIO 03

Pipeline de validação ⭐⭐⭐

⭐⭐⭐ — Grafo com loop de auto-correção

🎯 Objetivo Pedagógico

Grafo com loop: gerar → validar → corrigir se necessário → finalizar. Introduz o conceito de ciclo dentro de um grafo — a base para HITL (Human-in-the-Loop).

🔗 Conexão com a Aula 13

Este pipeline de auto-correção é a versão sem intervenção humana do HITL. Na Aula 13, substituímos o no_validar por um interrupt_before — onde um humano aprova ou rejeita a resposta antes de continuar.

1 Copiar e executar — Pipeline de validação
ex3_pipeline_validacao.py
from typing_extensions import TypedDict
from langchain_ollama import ChatOllama
from langgraph.graph import StateGraph, END

llm = ChatOllama(model="gpt-oss:120b", base_url="https://ollama.com.brcloud.com.br/v1")

# 1) Estado do pipeline
class EstadoPipeline(TypedDict):
    pergunta: str
    rascunho: str
    validado: bool
    resposta_final: str
    iteracoes: int

# 2) Nó de geração
def no_gerar(e):
    r = llm.invoke(e["pergunta"]).content
    return {"rascunho": r, "iteracoes": e.get("iteracoes", 0) + 1}

# 3) Nó de validação
def no_validar(e):
    check = llm.invoke(
        f"A resposta é clara e relevante?\nP:{e['pergunta']}\nR:{e['rascunho']}\nSIM ou NAO"
    ).content
    return {"validado": "SIM" in check.upper()}

# 4) Nó de correção
def no_corrigir(e):
    r = llm.invoke(f"Melhore a resposta.\nP:{e['pergunta']}\nAtual:{e['rascunho']}").content
    return {"rascunho": r}

# 5) Nó final
def no_final(e):
    return {"resposta_final": e["rascunho"]}

# 6) Função de decisão
def decidir(e):
    if e["validado"] or e.get("iteracoes", 0) >= 3:
        return "finalizar"
    return "corrigir"

# 7) Montar o grafo
g2 = StateGraph(EstadoPipeline)
g2.add_node("gerar", no_gerar)
g2.add_node("validar", no_validar)
g2.add_node("corrigir", no_corrigir)
g2.add_node("finalizar", no_final)
g2.set_entry_point("gerar")
g2.add_edge("gerar", "validar")
g2.add_conditional_edges("validar", decidir)
g2.add_edge("corrigir", "validar")
g2.add_edge("finalizar", END)

pipeline = g2.compile()

# 8) Testar
r = pipeline.invoke({
    "pergunta": "O que é RAG?",
    "rascunho": "",
    "validado": False,
    "resposta_final": "",
    "iteracoes": 0,
})
print(f"Iterações: {r['iteracoes']} | Validado: {r['validado']}")
print(f"R: {r['resposta_final'][:200]}")
saída esperada
Iterações: 2 | Validado: True
R: RAG (Retrieval-Augmented Generation) é uma técnica que combina recuperação de documentos com geração de texto...

💡 O que aconteceu?

O pipeline gera uma resposta, valida com o LLM, e corrige se necessário — até atingir a qualidade ou o limite de 3 iterações. O decidir() é a chave: ele observa o estado e decide se continua o loop ou finaliza.

2 Entenda o padrão
ComponenteFunçãoExemplo
Loop de iteraçãoRepete até atingir critériogerar → validar → corrigir → validar
Contador de iteraçõesEvita loop infinitoe.get("iteracoes", 0) >= 3
Função de decisãoEsclarece o próximo passodecidir() retorna "finalizar" ou "corrigir"
Validação externaVerifica qualidadeno_validar() usa LLM para avaliar

⚠️ Erros Comuns

1. Loop infinito — Se esquecer o limite de iterações (e.get("iteracoes", 0) >= 3), um pipeline que nunca valida com sucesso entra em loop eterno.

2. "KeyError: 'rascunho'" — O estado inicial precisa ter todos os campos. Passe {"pergunta": "...", "rascunho": "", "validado": False, "resposta_final": "", "iteracoes": 0}.

3. Val sempre retorna True — Se o prompt de validação for vago, o LLM pode sempre responder "SIM". Seja específico: "A resposta é clara, relevante e completa? Responda SOMENTE SIM ou NAO."

4. Correção não melhora — Se o prompt de correção não for claro, o LLM pode gerar uma resposta pior. Inclua o contexto: "Melhore a resposta considerando: clareza, completude e relevância."

5. Grafo não termina — Se decidir() nunca retornar "finalizar" (por lógica incorreta), o grafo fica preso. Teste com uma pergunta simples antes de escalar.

💡 Discussão com o Grupo

Esse padrão de auto-correção com loop é a base conceitual do HITL (Human-in-the-Loop) que veremos na Aula 13 — só que ali, quem aprova é um humano, não outra chamada ao LLM.
