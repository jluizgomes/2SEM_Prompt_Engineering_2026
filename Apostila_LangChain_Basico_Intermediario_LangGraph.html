Fundamentos

Os blocos de construção de qualquer aplicação LangChain: models, prompts, parsers e o operador que os une — LCEL.

1O que é LangChain

Básico Fundamentos

LangChain é um framework Python (e JavaScript) que padroniza como aplicações conversam com LLMs. Ele resolve três problemas que aparecem assim que você tenta ir além de uma chamada de API isolada:

  • Troca de provedor sem reescrever tudo — trocar de Ollama para OpenAI ou Anthropic é, na maioria dos casos, uma linha de código.
  • Composição de etapas — prompt → modelo → parser → próxima etapa, sem código repetitivo de "pegar o texto e passar para frente".
  • Integração com o ecossistema — vector stores, document loaders, tools e agentes já vêm com interface padronizada.
LangChain vs. LangGraph vs. Deep Agents
A documentação oficial apresenta os três como camadas: Deep Agents é "bateria inclusa" (contexto automático, sistema de arquivos virtual, subagentes) para quem quer o máximo de funcionalidade pronta. LangChain (com create_agent) é um harness mínimo e configurável — você compõe só o que precisa. LangGraph é a camada mais baixa: o motor de grafos de estado que sustenta os outros dois. Esta apostila ensina LangChain primeiro, depois desce para LangGraph — para você entender o que tem por baixo do capô antes de usar os atalhos.

3Chat Models

Básico Fundamentos

Um Chat Model é a interface padronizada do LangChain para conversar com um LLM. Não importa se por baixo é Ollama, OpenAI ou Anthropic — o código que você escreve é o mesmo. Isso é chamado de interface unificada.

chat_models.py
from langchain_core.messages import HumanMessage, SystemMessage, AIMessage

# Forma 1 — string direta
resposta = llm.invoke("O que é RAG?")

# Forma 2 — lista de mensagens tipadas (recomendado)
mensagens = [
    SystemMessage(content="Você é um assistente técnico conciso."),
    HumanMessage(content="O que é RAG?"),
]
resposta = llm.invoke(mensagens)

print(resposta.content)       # o texto da resposta
print(resposta.response_metadata)  # tokens, modelo usado, etc.

Parâmetros importantes

ParâmetroEfeitoValor típico
temperatureAleatoriedade da resposta. 0 = determinístico, 1.5 = muito criativo0.0–0.3 para tarefas precisas · 0.7+ para criativas
modelQual modelo usargpt-oss:120b neste curso
num_predictLimite de tokens gerados (equivalente a max_tokens)200–500 para respostas curtas

Streaming — respostas token a token

streaming.py
for chunk in llm.stream("Explique embeddings em 3 frases"):
    print(chunk.content, end="", flush=True)

Útil em interfaces (como Gradio) onde você quer mostrar a resposta sendo "digitada" em tempo real, em vez de esperar a resposta completa.

✏️ Pratique
Crie um SystemMessage com uma persona do domínio do seu grupo (saúde, educação, finanças...) e teste com 3 perguntas diferentes usando temperature=0.0 e depois temperature=1.0 — compare como a mesma pergunta gera respostas diferentes.

4Prompt Templates

Básico Fundamentos

Escrever prompts como f-strings soltas funciona para testes rápidos, mas não escala: fica difícil reutilizar, versionar ou trocar variáveis com segurança. ChatPromptTemplate resolve isso.

prompt_templates.py
from langchain_core.prompts import ChatPromptTemplate

template = ChatPromptTemplate.from_messages([
    ("system", "Você é especialista em {dominio}. Seja direto e use exemplos."),
    ("human", "{pergunta}"),
])

# .invoke() do template só monta as mensagens — ainda não chama o LLM
mensagens_prontas = template.invoke({
    "dominio": "cardiologia",
    "pergunta": "O que é arritmia?"
})

# Para chamar o modelo, combine com o LLM (veremos isso melhor no Cap. 6 — LCEL)
resposta = llm.invoke(mensagens_prontas)

Templates com histórico de mensagens

Um padrão muito comum é reservar um "espaço" no template para o histórico de conversa, usando MessagesPlaceholder:

placeholder.py
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

template = ChatPromptTemplate.from_messages([
    ("system", "Você é um assistente útil."),
    MessagesPlaceholder(variable_name="historico"),
    ("human", "{pergunta}"),
])

# historico é uma lista de HumanMessage/AIMessage — veremos isso no Cap. 8 (Memória)
from_template vs. from_messages
PromptTemplate.from_template("...") é para modelos de texto puro (legado). ChatPromptTemplate.from_messages([...]) é o padrão atual — todo Chat Model moderno (incluindo Ollama) espera uma lista de mensagens com role definido, não um texto solto.

5Output Parsers

Básico Fundamentos

Por padrão, o LLM retorna um objeto AIMessage — você precisa acessar .content toda vez. Um Output Parser automatiza essa extração e pode até validar o formato.

output_parsers.py
from langchain_core.output_parsers import StrOutputParser, JsonOutputParser

# StrOutputParser — extrai só o texto (o mais usado)
parser = StrOutputParser()

# JsonOutputParser — tenta parsear a resposta como JSON
json_parser = JsonOutputParser()
ParserQuando usar
StrOutputParserVocê só quer o texto puro da resposta — o caso mais comum
JsonOutputParserVocê pediu ao modelo para responder em JSON e quer o dict Python já parseado
with_structured_output()Você quer um objeto Pydantic validado — mais robusto que JsonOutputParser. Ver Capítulo 9.
⚠️ JsonOutputParser pode falhar
Se o modelo "conversar" antes do JSON (ex.: "Claro! Aqui está: {...}"), o JsonOutputParser pode quebrar. Para isso ser confiável, instrua explicitamente no system prompt: "Responda APENAS com JSON válido, sem texto antes ou depois." Para produção, prefira with_structured_output() (Capítulo 9), que é mais robusto.

6LCEL — o Operador Pipe

Básico Fundamentos · O conceito mais importante desta apostila

LCEL (LangChain Expression Language) é a forma padrão de compor chains: template | modelo | parser. O operador | (pipe) conecta cada etapa — a saída de uma vira a entrada da próxima, exatamente como pipes no terminal Linux.

lcel_basico.py
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

template = ChatPromptTemplate.from_messages([
    ("system", "Você é especialista em {dominio}."),
    ("human", "{pergunta}"),
])

# A chain inteira em uma linha
chain = template | llm | StrOutputParser()

# .invoke() roda o pipeline inteiro de uma vez
resposta = chain.invoke({
    "dominio": "nutrição",
    "pergunta": "Quantas calorias tem uma banana?"
})
print(resposta)  # já é string pura, graças ao StrOutputParser
Por que isso importa
Sem LCEL, você escreveria manualmente: montar o prompt → chamar .invoke() no modelo → extrair .content → validar formato. Com LCEL, isso é uma linha (chain = template | llm | parser) e o LangChain cuida da "cola" entre as etapas. É a mesma lógica de um pipeline Unix: cat arquivo.txt | grep erro | wc -l.

Chains com múltiplas etapas

LCEL não se limita a 3 etapas — você pode encadear quantas quiser, inclusive misturando funções Python comuns com RunnableLambda:

chain_multietapas.py
from langchain_core.runnables import RunnableLambda

def contar_palavras(texto: str) -> str:
    return f"{texto}\n\n[Resposta tem {len(texto.split())} palavras]"

# Insere uma função Python comum no meio do pipeline
chain = template | llm | StrOutputParser() | RunnableLambda(contar_palavras)

resultado = chain.invoke({"dominio": "história", "pergunta": "Quando foi a Revolução Francesa?"})
print(resultado)

invoke, batch e stream — os 3 modos de execução

MétodoUso
chain.invoke(x)Uma execução, espera a resposta completa. O que você mais vai usar.
chain.batch([x1, x2, x3])Roda múltiplas entradas em paralelo — muito mais rápido que um loop com invoke.
chain.stream(x)Retorna um generator que produz pedaços da resposta conforme chegam.
batch.py
# batch: 3 perguntas em paralelo, não sequencialmente
perguntas = [
    {"dominio": "saúde", "pergunta": "O que é febre?"},
    {"dominio": "saúde", "pergunta": "O que é hipertensão?"},
    {"dominio": "saúde", "pergunta": "O que é diabetes?"},
]
respostas = chain.batch(perguntas)
for r in respostas:
    print(r[:80])
✏️ Pratique
Monte uma chain LCEL de 4 etapas: template → llm → StrOutputParser → uma função sua que formata a resposta em maiúsculas ou adiciona um emoji. Teste com .batch() passando 3 perguntas diferentes do domínio do seu grupo.

7Runnables

Básico Fundamentos

Todo componente que você viu até agora — ChatPromptTemplate, ChatOllama, StrOutputParser — implementa a mesma interface: Runnable. É por isso que todos aceitam .invoke(), .batch() e .stream(), e é por isso que o operador | funciona entre eles.

A regra de ouro do LCEL
Se algo implementa .invoke(), é um Runnable — e pode entrar no pipe. Isso vale para templates, modelos, parsers, retrievers (Cap. 11), e para funções Python suas (via RunnableLambda). Uma vez que você entende isso, LCEL para de parecer mágica.

RunnableParallel — rodando etapas em paralelo

Às vezes você quer rodar 2+ etapas ao mesmo tempo e combinar os resultados — por exemplo, buscar contexto em uma base e reformular a pergunta do usuário, simultaneamente:

runnable_parallel.py
from langchain_core.runnables import RunnableParallel, RunnablePassthrough

# RunnablePassthrough repassa a entrada original sem alterar
chain_paralela = RunnableParallel(
    original=RunnablePassthrough(),
    maiusculas=RunnableLambda(lambda x: x.upper()),
    tamanho=RunnableLambda(lambda x: len(x)),
)

resultado = chain_paralela.invoke("prompt engineering")
# {'original': 'prompt engineering', 'maiusculas': 'PROMPT ENGINEERING', 'tamanho': 19}

Este padrão é exatamente o que você vai usar no Capítulo 12 (RAG) para buscar o contexto e passar a pergunta original ao mesmo tempo para o prompt final.

RunnableLambda — sua função vira um Runnable

runnable_lambda.py
from langchain_core.runnables import RunnableLambda

def validar_tamanho(texto: str) -> str:
    if len(texto) > 500:
        return texto[:500] + "... [truncado]"
    return texto

# Agora pode entrar em qualquer chain com |
chain = template | llm | StrOutputParser() | RunnableLambda(validar_tamanho)
RunnablePara quê
RunnableLambdaTransforma qualquer função Python num Runnable que entra no pipe
RunnableParallelRoda múltiplos Runnables ao mesmo tempo, combina os resultados num dict
RunnablePassthroughRepassa a entrada sem modificar — útil dentro de um RunnableParallel

8Memória Conversacional

Intermediário Corresponde à Aula 02

Um Chat Model, por si só, não lembra nada entre chamadas — cada .invoke() é isolado. "Memória" é você (ou o LangChain) reenviando o histórico relevante a cada novo turno.

A abordagem mais simples: lista de mensagens

memoria_buffer.py
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

class ChatbotComMemoria:
    def __init__(self, system_prompt):
        self.historico = [SystemMessage(content=system_prompt)]

    def chat(self, mensagem):
        self.historico.append(HumanMessage(content=mensagem))
        resposta = llm.invoke(self.historico)
        self.historico.append(AIMessage(content=resposta.content))
        return resposta.content

bot = ChatbotComMemoria("Você é um tutor de matemática paciente.")
print(bot.chat("O que é uma fração?"))
print(bot.chat("E como eu somo duas frações?"))  # lembra do contexto anterior

Isso é o que chamamos de Buffer Memory: guardar tudo. Funciona bem no início, mas o histórico cresce sem limite — e cresce o custo de tokens em cada chamada junto com ele.

As 3 estratégias que vocês já praticaram

EstratégiaComo funcionaQuando usar
BufferGuarda o histórico completoConversas curtas, onde custo não é problema
WindowGuarda só as últimas N mensagensConversas longas onde só o contexto recente importa
SummaryResume o histórico antigo em texto curto, mantém as últimas mensagens completasConversas muito longas, quando fatos antigos ainda importam
memoria_window.py
class ChatbotWindow:
    def __init__(self, system_prompt, window_size=6):
        self.system = system_prompt
        self.window_size = window_size
        self.historico = []  # lista de tuplas (user, ai)

    def chat(self, mensagem):
        # só as últimas window_size trocas entram no contexto
        janela = self.historico[-self.window_size:]
        mensagens = [SystemMessage(content=self.system)]
        for u, a in janela:
            mensagens += [HumanMessage(content=u), AIMessage(content=a)]
        mensagens.append(HumanMessage(content=mensagem))

        resposta = llm.invoke(mensagens)
        self.historico.append((mensagem, resposta.content))
        return resposta.content
⚠️ Nota sobre a API de Memory do LangChain
Versões antigas do LangChain tinham classes prontas como ConversationBufferMemory — hoje deprecadas. A abordagem atual (e a que vocês usam no curso) é gerenciar o histórico manualmente com uma lista de mensagens, como nos exemplos acima, ou — em LangGraph — usar um checkpointer (Capítulo 18), que é a forma recomendada para produção.
✏️ Pratique
Implemente a estratégia Summary: quando o histórico passar de 8 mensagens, chame o LLM para resumir as mais antigas em 2 frases, mantenha só as últimas 4 completas + o resumo como uma SystemMessage extra.

9Structured Output + Pydantic v2

Intermediário Corresponde à Aula 03

Pedir "responda em JSON" no prompt funciona às vezes. with_structured_output() é a forma robusta: você define um schema Pydantic, o LangChain garante que a resposta seja validada contra ele.

structured_output.py
from pydantic import BaseModel, Field
from typing import Literal

class AnaliseSentimento(BaseModel):
    sentimento: Literal['positivo', 'negativo', 'neutro']
    confianca: float = Field(ge=0.0, le=1.0)
    palavras_chave: list[str] = Field(description="até 3 palavras que justificam a análise")

# Vincula o schema ao modelo
llm_estruturado = llm.with_structured_output(AnaliseSentimento)

resultado = llm_estruturado.invoke("O atendimento foi péssimo, esperei 40 minutos.")
print(resultado.sentimento)      # 'negativo' — já é um objeto Python, não um dict
print(resultado.confianca)       # 0.92 (exemplo)
print(type(resultado))          # <class 'AnaliseSentimento'>
Por que isso é melhor que JsonOutputParser
with_structured_output() valida os tipos (o Literal garante que só um dos 3 valores é aceito, o Field(ge=0, le=1) garante o range numérico) e retorna um objeto Python tipado — com autocomplete no editor — em vez de um dict genérico que pode ter qualquer coisa dentro.

Combinando com LCEL

structured_lcel.py
chain = template | llm.with_structured_output(AnaliseSentimento)

resultado = chain.invoke({"dominio": "atendimento", "pergunta": "..."})
# resultado já é um objeto AnaliseSentimento — sem parser adicional

field_validator — validação customizada

field_validator.py
from pydantic import BaseModel, field_validator

class Contato(BaseModel):
    email: str

    @field_validator('email')
    @classmethod
    def validar_email(cls, v):
        if '@' not in v:
            raise ValueError('Email inválido')
        return v.lower().strip()
✏️ Pratique
Crie um schema Pydantic para um caso do domínio do seu grupo (ex.: TriagemPaciente, AnaliseContrato) com pelo menos 4 campos e 1 field_validator. Teste com 3 inputs diferentes.

10Document Loaders e Text Splitters

Intermediário Corresponde à Aula 05

Antes de indexar qualquer documento numa base vetorial, ele precisa ser: carregado, dividido em pedaços (chunks) de tamanho gerenciável.

Text Splitting

text_splitter.py
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,        # tamanho alvo de cada chunk, em caracteres
    chunk_overlap=80,       # sobreposição entre chunks consecutivos
    separators=['\n\n', '\n', '. ', ' '],  # tenta quebrar nesta ordem de preferência
)

texto = ("Documento longo aqui...\n\n"
         "com múltiplos parágrafos...")

chunks = splitter.split_text(texto)
print(f"Gerados {len(chunks)} chunks")
Por que "Recursive"?
O splitter tenta quebrar primeiro nos separadores "mais fortes" (parágrafos \n\n), e só recorre a separadores mais fracos (frase, espaço) se o chunk ainda estiver grande demais. Isso preserva unidades semânticas completas sempre que possível — em vez de cortar uma frase no meio.

Chunk size — o trade-off central

Chunk pequeno (200-300)Chunk grande (1000+)
Busca mais precisa (menos ruído)Mais contexto por resultado
Pode perder contexto ao redorBusca menos precisa (mais ruído misturado)
Mais chunks = mais tempo de indexaçãoMenos chunks = indexação mais rápida

Não existe valor universal certo — o CKP02 pede exatamente que vocês comparem 2+ configurações com métricas RAGAS (Capítulo 12) em vez de adivinhar.

11Embeddings e Vector Stores

Intermediário Corresponde à Aula 05

Embedding é a representação de um texto como um vetor de números — textos com significado parecido geram vetores próximos no espaço. É isso que permite "busca por significado" em vez de busca por palavra-chave exata.

embeddings.py
from ollama import Client

client = Client(host='https://ollama.com', headers={'Authorization': 'Bearer ' + userdata.get('OLLAMA_API_KEY')})

def embedding(texto):
    return client.embeddings(model='nomic-embed-text', prompt=texto)['embedding']

vetor = embedding("O que é hipertensão?")
print(len(vetor))  # 768 dimensões, típico do nomic-embed-text
⚠️ nomic-embed-text é o único modelo de embedding aprovado no curso
Gratuito via Ollama Cloud, consistente em todos os notebooks. Não misture modelos de embedding diferentes no mesmo índice — os espaços vetoriais não são compatíveis entre modelos.

ChromaDB — indexação e busca

chromadb_basico.py
!pip install -q chromadb
import chromadb

chroma = chromadb.Client()  # em memória — some ao reiniciar o Colab
# chroma = chromadb.PersistentClient(path="./minha_base")  # persiste em disco

colecao = chroma.create_collection("documentos_dominio")

documentos = ["Protocolo de triagem para febre alta.", "Diretriz de hidratação em pacientes idosos."]
colecao.add(
    documents=documentos,
    ids=[f"doc{i}" for i in range(len(documentos))],
    embeddings=[embedding(d) for d in documentos],
)

resultado = colecao.query(query_embeddings=[embedding("o que fazer com febre?")], n_results=2)
print(resultado['documents'][0])

Similaridade cosseno — o que acontece por dentro

cosine_similarity.py
import math

def cosine_sim(a, b):
    dot = sum(x*y for x, y in zip(a, b))
    norma_a = math.sqrt(sum(x*x for x in a))
    norma_b = math.sqrt(sum(x*x for x in b))
    return dot / (norma_a * norma_b)

# Resultado entre -1 e 1. Próximo de 1 = muito similar semanticamente.

O ChromaDB faz isso internamente e de forma otimizada — mas entender a matemática por baixo ajuda a debugar quando a busca "não está encontrando o óbvio".

12RAG Completo

Intermediário Corresponde às Aulas 06–07 · CKP02

RAG (Retrieval-Augmented Generation) junta tudo dos Capítulos 10–11 num pipeline: busca documentos relevantes → injeta como contexto no prompt → o LLM responde fundamentado nesse contexto, não só no que já "sabe".

rag_pipeline.py
def rag(pergunta, k=3):
    # 1. RETRIEVE — busca os k chunks mais relevantes
    resultado = colecao.query(query_embeddings=[embedding(pergunta)], n_results=k)
    contexto = '\n---\n'.join(resultado['documents'][0])

    # 2. AUGMENT — injeta o contexto no prompt
    prompt = (
        f"Responda com base APENAS no contexto abaixo. "
        f"Se não souber, diga que não encontrou a informação.\n\n"
        f"Contexto:\n{contexto}\n\nPergunta: {pergunta}"
    )

    # 3. GENERATE — o LLM responde fundamentado
    resposta = llm.invoke(prompt, temperature=0.1)  # temperatura baixa = menos invenção
    return resposta.content, resultado['documents'][0]

resposta, fontes = rag("Qual o protocolo para febre alta?")
print(resposta)

RAG com LCEL — a versão idiomática

rag_lcel.py
from langchain_core.runnables import RunnableParallel, RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

def buscar_contexto(pergunta: str) -> str:
    res = colecao.query(query_embeddings=[embedding(pergunta)], n_results=3)
    return '\n---\n'.join(res['documents'][0])

template_rag = ChatPromptTemplate.from_messages([
    ("system", "Responda com base no contexto. Se não souber, diga que não encontrou."),
    ("human", "Contexto:\n{contexto}\n\nPergunta: {pergunta}"),
])

# RunnableParallel monta o dict {contexto, pergunta} que o template espera
rag_chain = (
    RunnableParallel(
        contexto=RunnableLambda(buscar_contexto),
        pergunta=RunnablePassthrough(),
    )
    | template_rag
    | llm
    | StrOutputParser()
)

resposta = rag_chain.invoke("Qual o protocolo para febre alta?")

def faithfulness(resposta, contextos):
    v = llm.invoke(f"A resposta é suportada pelo contexto? Contexto: {contextos}\nResposta: {resposta}\nSIM ou NAO")
    return 'SIM' in v.content.upper()
✏️ Pratique — direto para o CKP02

13Tools

Intermediário Corresponde à Aula 09

Uma Tool é uma função Python que um agente pode decidir chamar. Você escreve a função normalmente e decora com @tool — o LangChain usa o docstring e as anotações de tipo para o LLM entender quando e como usar.

tools.py
from langchain_core.tools import tool
import math

@tool
def calcular_imc(peso_kg: float, altura_m: float) -> str:
    """Calcula o IMC (Índice de Massa Corporal) e retorna a classificação."""
    imc = peso_kg / (altura_m ** 2)
    categoria = 'abaixo do peso' if imc < 18.5 else 'normal' if imc < 25 else 'sobrepeso'
    return f"IMC: {imc:.1f} ({categoria})"

# Testando a tool diretamente, sem passar pelo LLM
print(calcular_imc.invoke({'peso_kg': 70.0, 'altura_m': 1.75}))
print(calcular_imc.name)          # 'calcular_imc'
print(calcular_imc.description)   # o docstring vira a descrição que o LLM lê
⚠️ O docstring não é decoração — é a interface
O LLM decide se e quando chamar sua tool lendo o docstring. Um docstring vago ("faz um cálculo") gera decisões erradas. Seja específico: o que a função faz, quando usá-la, o que ela NÃO faz.

Vinculando tools a um modelo

bind_tools.py
tools = [calcular_imc]
llm_com_tools = llm.bind_tools(tools)

resposta = llm_com_tools.invoke("Qual o IMC de alguém com 80kg e 1.80m?")

# O modelo NÃO executa a tool sozinho — ele só *pede* para executar
print(resposta.tool_calls)
# [{'name': 'calcular_imc', 'args': {'peso_kg': 80.0, 'altura_m': 1.8}, 'id': '...'}]

# Você (ou um agente) precisa executar de fato e devolver o resultado
for chamada in resposta.tool_calls:
    resultado = calcular_imc.invoke(chamada['args'])
    print(resultado)

Esse "pedir mas não executar" é o ponto-chave: o LLM decide qual tool chamar e com quais argumentos, mas quem executa o código de fato é o seu programa (ou o loop de um agente — Capítulo 14).

14Agentes — do Manual ao create_agent

Intermediário Corresponde às Aulas 09–11 · CKP03

Um agente repete o ciclo Reason → Act → Observe (ReAct): o LLM raciocina sobre o que fazer, chama uma tool, observa o resultado, e decide se precisa de mais uma chamada ou se já pode responder.

Nível 1 — o loop ReAct manual

Entender o loop manualmente antes de usar atalhos é o que separa quem sabe debugar um agente de quem só copia código:

agente_manual.py
from langchain_core.messages import HumanMessage, SystemMessage, ToolMessage

tools_map = {t.name: t for t in tools}

def agente_react(pergunta, max_steps=5):
    mensagens = [
        SystemMessage(content="Use as tools disponíveis quando necessário."),
        HumanMessage(content=pergunta),
    ]
    for _ in range(max_steps):
        resposta = llm_com_tools.invoke(mensagens)

        # Sem tool_calls = o modelo decidiu que já pode responder
        if not resposta.tool_calls:
            return resposta.content

        mensagens.append(resposta)
        for chamada in resposta.tool_calls:
            resultado = tools_map[chamada['name']].invoke(chamada['args'])
            mensagens.append(ToolMessage(content=str(resultado), tool_call_id=chamada['id']))

    return "Limite de passos atingido"
Este é exatamente o loop dos notebooks do curso
O padrão acima é o mesmo usado nas Aulas 09–11: bind_tools + loop manual verificando tool_calls. É deliberadamente de baixo nível — para vocês entenderem o mecanismo antes de usar abstrações prontas.

Nível 2 — create_agent (a API atual do LangChain)

A documentação oficial (2026) recomenda create_agent como o ponto de entrada padrão para construir agentes — ele encapsula exatamente o loop acima, já pronto e testado, e é construído sobre LangGraph por baixo dos panos (o que veremos na Parte 3).

create_agent.py
from langchain.agents import create_agent

agente = create_agent(
    model=llm,
    tools=[calcular_imc],
    system_prompt="Você é um assistente de saúde. Use as tools quando precisar calcular algo.",
)

# invoke espera um dict com 'messages'
resultado = agente.invoke({"messages": [HumanMessage(content="IMC de alguém com 90kg e 1.70m?")]})
print(resultado["messages"][-1].content)

LangGraph

A camada por baixo do capô de create_agent: grafos de estado, roteamento condicional, memória persistente e aprovação humana.

15Por que LangGraph

LangGraph Corresponde à Aula 12

LCEL é ótimo para pipelines lineares: A → B → C, sempre na mesma ordem. Mas casos reais raramente são lineares:

  • "Se a pergunta for sobre X, vá para o nó A; se for sobre Y, vá para o nó B" — roteamento condicional
  • "Pause aqui e espere um humano aprovar antes de continuar" — human-in-the-loop
  • "Lembre o que aconteceu há 10 mensagens, mesmo se o processo reiniciar" — memória persistente entre sessões
  • "Volte para um passo anterior se a validação falhar" — loops

Nenhum desses padrões é natural em LCEL puro (que é uma cadeia linear). LangGraph resolve isso modelando o fluxo como um grafo de estado: nós (funções) conectados por arestas (que podem ser condicionais), operando sobre um estado compartilhado.

create_agent JÁ é um grafo
Quando vocês usaram create_agent no Capítulo 14, por baixo dos panos ele monta exatamente um StateGraph com um nó de modelo e um nó de tools, conectados por uma aresta condicional — o mesmo que vocês vão construir manualmente neste capítulo. Entender LangGraph explica o que create_agent faz por vocês.

16StateGraph — Nodes e Edges

LangGraph Corresponde à Aula 13

Três peças constroem qualquer grafo LangGraph: State (o que é compartilhado entre os nós), Node (uma função que lê e atualiza o estado) e Edge (a conexão entre nós).

stategraph_basico.py
from typing import TypedDict, Annotated, Sequence
from langchain_core.messages import BaseMessage, HumanMessage
from langgraph.graph import StateGraph, START, END
import operator

# 1. STATE — um TypedDict define o formato dos dados que fluem pelo grafo
class EstadoSimples(TypedDict):
    mensagens: Annotated[Sequence[BaseMessage], operator.add]  # operator.add = acumula, não sobrescreve

# 2. NODE — uma função que recebe o estado e retorna a atualização
def no_assistente(estado):
    resposta = llm.invoke(estado['mensagens'])
    return {'mensagens': [resposta]}

# 3. MONTAR O GRAFO
builder = StateGraph(EstadoSimples)
builder.add_node('assistente', no_assistente)
builder.add_edge(START, 'assistente')
builder.add_edge('assistente', END)

grafo = builder.compile()  # só depois de compilado o grafo pode rodar

resultado = grafo.invoke({'mensagens': [HumanMessage(content='O que é LangGraph?')]})
print(resultado['mensagens'][-1].content)
Por que Annotated[..., operator.add]?
Por padrão, quando um nó retorna um campo do estado, o LangGraph sobrescreve o valor antigo. Com operator.add como "reducer", o novo valor é concatenado à lista existente em vez de substituí-la — essencial para o campo de mensagens, onde cada nó adiciona à conversa em vez de apagar o histórico.

Grafo com múltiplos nós em sequência

grafo_sequencial.py
class EstadoPipeline(TypedDict):
    pergunta: str
    rascunho: str
    resposta_final: str

def gerar(estado):
    r = llm.invoke(estado['pergunta'])
    return {'rascunho': r.content}

def revisar(estado):
    r = llm.invoke(f"Revise e melhore: {estado['rascunho']}")
    return {'resposta_final': r.content}

builder = StateGraph(EstadoPipeline)
builder.add_node('gerar', gerar)
builder.add_node('revisar', revisar)
builder.add_edge(START, 'gerar')
builder.add_edge('gerar', 'revisar')   # sequência fixa: sempre gerar → revisar
builder.add_edge('revisar', END)

grafo = builder.compile()
✏️ Pratique
Construa um grafo de 3 nós em sequência: classificar (identifica o tipo da pergunta) → buscar_contexto (usa seu RAG do Capítulo 12) → responder.

17Conditional Edges

LangGraph Corresponde à Aula 13

Uma aresta condicional decide dinamicamente qual nó executar a seguir, baseada no estado atual — é isso que torna um grafo diferente de um pipeline linear.

conditional_edges.py
class EstadoAgente(TypedDict):
    mensagens: Annotated[Sequence[BaseMessage], operator.add]

def no_agente(estado):
    resposta = llm_com_tools.invoke(estado['mensagens'])
    return {'mensagens': [resposta]}

def no_tools(estado):
    ultima = estado['mensagens'][-1]
    resultados = []
    for chamada in ultima.tool_calls:
        r = tools_map[chamada['name']].invoke(chamada['args'])
        resultados.append(ToolMessage(content=str(r), tool_call_id=chamada['id']))
    return {'mensagens': resultados}

# A FUNÇÃO DE DECISÃO — retorna o NOME do próximo nó como string
def decidir_proximo_no(estado):
    ultima = estado['mensagens'][-1]
    if hasattr(ultima, 'tool_calls') and ultima.tool_calls:
        return 'tools'     # precisa executar uma tool
    return END          # já tem resposta final

builder = StateGraph(EstadoAgente)
builder.add_node('agente', no_agente)
builder.add_node('tools', no_tools)
builder.set_entry_point('agente')
builder.add_conditional_edges('agente', decidir_proximo_no)  # ramifica com base na decisão
builder.add_edge('tools', 'agente')  # após executar a tool, volta ao agente — LOOP

grafo_react = builder.compile()

Este é o mesmo padrão ReAct do Capítulo 14 — mas agora como um grafo explícito, com o loop visível (tools → agente) em vez de escondido dentro de um while.

Roteamento com múltiplos destinos

router_multiplo.py
def classificar_categoria(estado):
    if 'urgente' in estado['categoria']:
        return 'urgente'
    elif 'financeiro' in estado['categoria']:
        return 'financeiro'
    return 'geral'

# O dict mapeia o retorno da função para o nome real do nó

    'classificar',
    classificar_categoria,

18Checkpointer e Memória Persistente

LangGraph Corresponde à Aula 13

Um checkpointer salva o estado do grafo a cada passo, associado a um thread_id. Isso permite retomar exatamente de onde parou — mesmo em uma nova chamada de .invoke(), mesmo depois de reiniciar o processo (se usar um checkpointer persistente em disco/banco).

checkpointer.py
from langgraph.checkpoint.memory import InMemorySaver
# Alias comum em código mais antigo: MemorySaver — mesmo conceito

memory = InMemorySaver()
grafo_com_memoria = builder.compile(checkpointer=memory)

config = {'configurable': {'thread_id': 'usuario-alice'}}

# Primeira chamada
grafo_com_memoria.invoke({'mensagens': [HumanMessage(content='Meu nome é Alice.')]}, config)

# Segunda chamada, MESMO thread_id — lembra da primeira
r = grafo_com_memoria.invoke({'mensagens': [HumanMessage(content='Qual é o meu nome?')]}, config)
print(r['mensagens'][-1].content)  # "Seu nome é Alice"

# thread_id DIFERENTE = conversa completamente isolada
config_bob = {'configurable': {'thread_id': 'usuario-bob'}}
r2 = grafo_com_memoria.invoke({'mensagens': [HumanMessage(content='Qual é o meu nome?')]}, config_bob)
# Bob não tem contexto de Alice — thread_id separa sessões de usuários diferentes
thread_id = 1 sessão de usuário
Na prática (e no CKP03), cada usuário da sua interface Gradio deve ter um thread_id único e estável — pode ser o ID de sessão do Gradio, um UUID gerado no início da conversa, ou o ID do usuário logado.

InMemorySaver vs. persistência real

CheckpointerPersiste ondeSobrevive a reinício do Colab?
InMemorySaverRAM do processoNão — usado nos notebooks do curso
SqliteSaverArquivo SQLite localSim, se o arquivo persistir
PostgresSaverBanco PostgresSim — usado em produção real

19Human-in-the-Loop

LangGraph Corresponde à Aula 13

Nem toda decisão de um agente deveria ser automática. HITL (Human-in-the-Loop) pausa o grafo antes de uma ação crítica e espera aprovação humana antes de continuar.

Abordagem 1 — interrupt_before (mais simples)

interrupt_before.py
memory = InMemorySaver()

# O grafo PAUSA automaticamente antes do nó 'executar'
grafo_hitl = builder.compile(checkpointer=memory, interrupt_before=['executar'])

config = {'configurable': {'thread_id': 'aprovacao-001'}}

# PASSO 1 — roda até parar antes de 'executar'
r = grafo_hitl.invoke({'solicitacao': 'Enviar 500 emails de marketing', 'aprovado': False}, config)
print('[PAUSADO — aguardando aprovação humana]')

# PASSO 2 — humano aprova (ex.: um botão na interface)
grafo_hitl.update_state(config, {'aprovado': True})

# PASSO 3 — retoma de onde parou (None = continua sem nova entrada)
r2 = grafo_hitl.invoke(None, config=config)

Abordagem 2 — interrupt() dentro do nó (mais flexível)

interrupt_dinamico.py
from langgraph.types import interrupt, Command

def no_revisao_humana(estado):
    # A execução PARA aqui e devolve esta pergunta para quem chamou
    resposta = interrupt('Aprova o envio dos 500 emails? (sim/não)')
    return {'aprovado': resposta == 'sim'}

# Para retomar depois do interrupt, usa Command(resume=...)
grafo.invoke(Command(resume='sim'), config=config)
AbordagemQuando usar
interrupt_beforePausa sempre no mesmo nó, de forma previsível — mais simples de entender
interrupt() dentro do nóA pausa é condicional (só interrompe às vezes) ou precisa levar uma pergunta específica ao humano
✏️ Pratique
No agente do seu CKP03, identifique 1 ação que deveria pedir aprovação humana antes de executar (ex.: enviar algo, deletar algo, confirmar um valor alto) e implemente com interrupt_before.

20Multiagentes

LangGraph Avançado — não obrigatório no CKP03

Em vez de um único agente generalista, o padrão supervisor/worker divide responsabilidades: um nó supervisor decide qual agente especializado (worker) deve agir, cada worker é especialista em uma coisa só.

supervisor_worker.py
class EstadoMultiagente(TypedDict):
    mensagens: Annotated[Sequence[BaseMessage], operator.add]
    proximo: str

def supervisor(estado):
    # O supervisor só decide QUEM age, não age ele mesmo
    decisao = llm.invoke(
        f"Classifique em: rag, calculo ou geral. Só a palavra.\n{estado['mensagens'][-1].content}"
    )
    return {'proximo': decisao.content.strip().lower()}

def worker_rag(estado):
    resposta, _ = rag(estado['mensagens'][-1].content)  # do Capítulo 12
    return {'mensagens': [AIMessage(content=resposta)]}

def worker_calculo(estado):
    resposta = llm_com_tools.invoke(estado['mensagens'])
    return {'mensagens': [resposta]}

builder = StateGraph(EstadoMultiagente)
builder.add_node('supervisor', supervisor)
builder.add_node('worker_rag', worker_rag)
builder.add_node('worker_calculo', worker_calculo)
builder.set_entry_point('supervisor')
builder.add_conditional_edges(
    'supervisor',
    lambda estado: estado['proximo'],
    {'rag': 'worker_rag', 'calculo': 'worker_calculo', 'geral': END},
)
builder.add_edge('worker_rag', END)
builder.add_edge('worker_calculo', END)
Quando vale a pena
Multiagentes ajudam quando um único system prompt "faz tudo" fica confuso demais ou quando você quer isolar o contexto de cada especialidade (ex.: worker jurídico não precisa ver o histórico do worker técnico). Para a maioria dos projetos de CKP03, um único agente com boas tools já é suficiente — considere multiagentes só se sentir o system prompt ficando genérico demais.

21create_agent por Dentro

LangGraph Fechamento — conectando tudo

Voltando ao Capítulo 14: agora que vocês conhecem StateGraph, conditional edges e checkpointer, o que create_agent faz fica transparente. Ele monta, automaticamente, o mesmo grafo do Capítulo 17:

1. Um nó de modelo
Equivalente ao no_agente — chama o LLM com as tools vinculadas.
2. Um nó de tools
Equivalente ao no_tools — executa as chamadas pedidas pelo modelo.
3. Uma aresta condicional
Equivalente ao decidir_proximo_no — decide entre tools e END.
4. checkpointer= plugado direto
O parâmetro checkpointer= do Capítulo 14 é literalmente o mesmo do Capítulo 18.
Por que isso importa na prática
Quando o comportamento padrão de create_agent não for suficiente para o seu CKP03 — por exemplo, você precisa de um passo extra de validação antes de responder, ou de roteamento entre 2 personas diferentes — você sabe exatamente onde "abrir o capô" e escrever seu próprio StateGraph em vez de forçar o caso dentro de create_agent.
